# 性能指标与排队：带宽不是响应速度

## 指标描述的对象不同

RTT 为一次往返时间，不等于单向延迟的两倍，方向可能不对称。链路容量、可用带宽、实际吞吐量与应用有效载荷速率也不同：100 Mbps 除以 8 是理论 12.5 MB/s，协议开销与瓶颈会降低应用结果。RTT 很低仍可能下载慢，带宽很高仍可能交互慢。

丢包率需要明确采样对象和时间窗口。2000 个包丢 40 个是 2%，但连续丢 40 个与均匀丢失的体验可能不同；诊断 ICMP 被过滤不等价于业务 TCP 丢包率。UDP 不提供重传保证，不是“UDP 必然更快也必然丢包”的因果关系。

## 请求例子：顺序依赖放大 RTT

接口依次远程调用 5 次，每次网络往返约 40 ms，即使响应很小，也可能累计约 200 ms 网络等待，尚未包括计算、排队、TLS 等成本。能安全并行的独立调用可以减少关键路径；有事务依赖的步骤不能只为提速随意并行。

传输 10 MiB 数据到可用吞吐 10 Mbit/s 的路径，纯传输下限约 8.39 秒，另加连接与其他开销。区分 MiB 的 2^20 字节与 MB 的 10^6 字节，不能混用单位后得出精确测速结论。

## 排队与缓冲不是免费补偿

当发送速率长期超过瓶颈可服务速率，队列积累导致等待增加，队列满后丢包。更大的缓冲可以吸收突发，却不能提高瓶颈服务能力，反而可能让交互延迟更高。RTT 上升、抖动、丢包可能同源于拥塞，但无线干扰也可直接丢包，不存在唯一的固定先后链。

实时音视频接收端用抖动缓冲平滑到达波动，缓冲越大通常更能吸收迟到，但延迟也更高。IP 包时延变化与 RTP jitter 有各自定义，不能把“ping 最大值减最小值”直接当所有场景的标准抖动。

## WebRTC 如何测量

`availableOutgoingBitrate` 是路径可用发送比特率的估计，不是网卡上限也不是实际发送速率，字段可能不可用。两次 stats 的 bytesSent 差除时间差，再乘 8，才能估计对应统计对象区间平均比特率；注意 timestamp 单位是毫秒，需换算秒。

```javascript
function intervalBitrate(previous, current) {
  const seconds = (current.timestamp - previous.timestamp) / 1000;
  if (seconds <= 0 || current.bytesSent < previous.bytesSent) return null;
  return 8 * (current.bytesSent - previous.bytesSent) / seconds;
}
```

比较前确认是同一统计对象，连接重建或计数重置后重新建立基线。采样 RTP、传输层或候选对的字节口径不同，不能简单相加当单一媒体有效速率。

## 拓展与工程判断

后端接口统计 p50/p95/p99 与错误率，而不只平均耗时；平均值会隐藏长尾。压测必须记录并发、请求速率、数据大小和连接复用方式。先定位瓶颈是计算、磁盘、数据库、连接池还是网络，再选择缓存、批量、并行或降码率；扩大带宽不能修复数据库锁等待。
