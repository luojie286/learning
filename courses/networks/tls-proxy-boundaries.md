# TLS、代理与信任边界

## 加密连接必须连到预期的人

TLS 为通信提供保密性、完整性与对端认证机制。典型网站连接用证书和签名认证服务端，通过临时密钥协商派生对称密钥保护数据。证书不负责直接加密所有 HTTP 正文，证书链也不是只验一次签名就完事；还要看域名 SAN、有效期、用途、信任锚及客户端策略。

正常证书验证可阻止单纯 DNS 重定向冒充原域名。攻击者若能让客户端接受伪造证书，并控制连接路径，可能分别建立客户端—攻击者、攻击者—真实站两条 TLS，读取自身作为终点的明文。地址栏域名未必改变，因此“看起来网址没变”不足以验证身份。

TLS 1.3 的常见临时密钥交换提供前向保密，后来仅泄露网站证书私钥不等于能解密过去全部流量。不能把该结论扩成所有配置、PSK 模式或终端泄露下的绝对保证。

## CONNECT 与 SOCKS5 转发什么

浏览器通过 HTTP 代理访问 HTTPS，可先发 `CONNECT example.com:443`，代理成功后在隧道内与目标进行 TLS。HTTPS_PROXY 配成 `http://127.0.0.1:7897` 描述的是连接代理的方法，不代表最终站点 HTTPS 被改成明文。端口号由本机代理配置决定，不是标准固定值。

SOCKS5 支持 CONNECT 等命令并定义 UDP ASSOCIATE，本身不保证数据加密。传域名可由代理侧解析；先本地解析再传 IP 会影响 DNS 路径。普通隧道代理不能自动看到 HTTPS 明文；若终端另行信任了拦截代理的 CA，则情况不同。

## VPN、TUN 与规则不是同一概念

VPN 可将内层 IP 包加密封装送往隧道端点，外部网络主要看到外层端点与流量特征。TUN 是供用户程序收发三层数据包的虚拟接口机制，不等于一种具体加密协议；TAP 则面向以太帧。

全隧道或分流取决于路由、DNS、IPv6 与排除规则。“全局模式”也可能仅对交给代理的流量生效，不代表所有进程所有协议都已接管。Fake-IP 是代理内部维护域名映射的一种实现策略，不是目标站点真正的公网部署地址；其具体地址段与规则应查对应客户端配置。

## 后端部署例子：TLS 在哪里结束

浏览器经 HTTPS 访问 Nginx，再由 Nginx 通过 HTTP 转发本机 Spring Boot。公网 TLS 的终点是 Nginx，内部一跳未必加密；跨不可信网络时要为内部链路另设保护。日志和转发头必须由可信入口规范处理，不能无条件信任客户端伪造的 X-Forwarded-For/Proto。

VPN 出口一般还能观察目标地址等元数据，但正常站点 TLS 明文仍由真实 TLS 终点掌握。网站仍可通过登录身份和应用标识识别用户，换出口 IP 不等于完全匿名。

## 漏洞判断基于条件

原稿所提具体 2026 漏洞缺少已核实编号和影响版本，不作为事实收录。应从官方公告核对组件、版本、触发路径、暴露面与修复；存在 CVE 不等于项目可远程攻击，也不等于已泄露。Node.js 是运行时，Express/Spring 是框架，GitHub Pages 托管静态内容，构建使用某运行时不代表线上 API 运行在它上面。

不要为了连接成功关闭证书验证，这会破坏身份保证；应检查服务器证书链、时间、域名与受信任根配置。
