# 死锁、资源顺序与安全状态

## 等待为什么永远不能推进

A 持锁 L1 等 L2，B 持锁 L2 等 L1，构成循环等待。教材资源模型中死锁需要互斥、占有且等待、不可抢占、循环等待同时存在；统一资源顺序可以打破环路。这里的“不可抢占”指资源不能安全强取，不是 CPU 不能时间片抢占。

死锁不一定非得两个不同线程：一个线程重复获取不支持重入的锁，也可能自我等待。饥饿是长期得不到机会而其他任务仍推进；活锁是双方不断让步或重试却没有进展；死循环可能在消耗 CPU。这些现象应通过等待关系与进度判断，不能只看“卡住”。

## 后端例子：账户转账

T1 从账户 A 转给 B，先锁 A 再锁 B；T2 反向转账先锁 B 再锁 A，会形成环。按账户 ID 从小到大加锁，再在临界区内按业务方向变更金额，可破坏循环等待。相同账户需单独处理，数据库行锁顺序、事务边界及实际访问计划也要一致。

仅设置锁超时不一定杜绝死锁，但可使调用放弃等待；放弃时应回滚已改状态并释放资源，重试要限制次数并带退避。不能杀掉持锁线程就假定数据自动恢复一致；Java finally、数据库事务回滚和外部副作用分别有不同保证。

## 避免不是预防

预防改变资源规则，避免在每次分配前判断是否仍安全。银行家算法假设最大需求已知，Need=Max-Allocation，先检查请求不超过声明需求且当前可用，然后试分配并模拟安全序列。安全性检查使用独立 Work，找到 Need<=Work 的未完成进程后假设完成，Work+=其当前 Allocation。

单资源例：总量 10，P0 已持 3 最多需 9，P1 已持 2 最多需 4，Available=5。P1 还需 2，可以完成后归还 2，Work 变 7；P0 还需 6，随后可完成，故存在安全序列 P1→P0。若先再给 P0 三份，可用变 2，P1 仍能完成；若把剩余都给 P0，则可用为 0，而 P0/P1 都还需 1/2，试分配不安全，应拒绝。

不安全表示在该最大需求模型下无法保证所有任务最终完成，并不等于已经发生实际死锁；任务可能根本不再申请其最大值。银行家在一般互联网业务中难获完整需求，因此常使用事务死锁检测与重试，而不是把它当所有数据库的实际算法。

## 图检测与恢复

资源分配图 P→R 表请求，R→P 表已分配。每类单实例时，有环可判死锁；多实例有环只是必要线索，可能仍有可释放的实例。使用等待图也要说明建图规则与资源模型，不能看任意业务依赖图的环就宣布进程死锁。

检测到后可选择中止事务、回滚或在可恢复的模型下抢占资源。选择受害者考虑已做工作、重要性与饥饿，重复杀同一事务可能造成另一种不公平。

## 优先级倒置不是同一问题

低优先级 L 持锁，高优先级 H 等锁，中优先级 M 抢占 L，使 H 被间接延迟。优先级继承暂时提高持锁 L 的调度优先级，让它更快完成释放；不把锁强行转给 H，不能据此解决循环等待。支持该协议的锁和调度配置才会生效，普通 Java 锁不能自动假设具有 OS 实时优先级继承。
