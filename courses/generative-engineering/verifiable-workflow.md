# 可验证的生成式开发流程

## 先约束问题，不要先规定唯一架构

原稿“首先对项目约束、前后端分离”是一条项目偏好，不是软件工程普遍定律。静态博客可以直接 HTML/CSS/JS，复杂独立客户端和 API 可能适合分离；要根据部署、权限、团队和维护需求选择。把必须条件写成可检验行为，把偏好写成可讨论取舍。

例如订单查询改造：接口返回字段与权限规则是约束，使用某种缓存是设计选择，响应时间是要在指定负载下验证的指标。模型输出更多代码不代表完成更多有效工作。

## 四类验证器的能力边界

| 类型 | 检查方式 | 可以发现 | 不能自动保证 |
|---|---|---|---|
| 规则验证 | Schema、静态规则、文件边界 | 字段缺失、格式错误 | 业务内容真实正确 |
| 程序验证 | 执行测试、构建、差分比较 | 已覆盖条件下的错误 | 未覆盖场景永远正确 |
| 模型评审 | 根据标准提出判断与疑点 | 部分遗漏、表达与推理问题 | 独立客观事实与完全可靠性 |
| 形式方法 | 在模型和前提下证明性质 | 所表达性质的违反 | 规范正确及所有现实环境匹配 |

“模型再评一次”可能与生成器共享错误偏差，不能当成已经获得独立证明。训练 verifiers 的研究在特定数学题场景有效，也不等于通用软件验证器已能判定所有程序性质。

## 开发例子：订单越权缺陷

目标是用户 A 不能读取 B 的订单。先写测试：合法会话读取自己订单成功；读取别人的订单返回约定拒绝；不存在订单与未登录有独立语义。规则验证确保响应 Schema，程序测试检查授权行为，人工评审追踪 userId 是否来自可信会话而非请求参数。

```text
输入：可信会话 subject=A，请求 orderId=属于B的订单。
预期：拒绝，不返回订单明细。
证据：控制器调用 → 服务层所有者校验 → Repository 查询条件。
反例：把 userId=A 改成 userId=B 不应改变授权主体。
```

只测“返回 200 且 JSON 正确”会错过越权。测试应与风险相关，而不是机械逐行照抄实现。错误修复还需评估其他调用路径是否绕过相同校验。

## 把长任务拆成可交付阶段

先调查现状与边界，再实现最小完整行为，随后运行相关检查、查看差异并记录限制。每阶段保存修改范围、验证结果和未完成项；一个阶段失败时根据证据修复，不靠反复要求模型“更认真”。

代码生成前列出不能动的目录、接口兼容要求和敏感资源边界。生成后检查差异是否越界、是否添加无依据依赖、是否把示例凭据写入代码。工具成功只说明工具动作完成，截图看起来好也不证明交互可用；分别为结果选择合适证据。

## 评估与成本

构造包含正常、边界、失败和历史回归的任务集，固定评价标准再比较提示或工作流。记录通过率之外的错误类型、人工审核成本与运行时间；重试越多不一定更省钱，也可能重复错误。高影响结果需要更强证据，但小幅可逆文案无需添加繁重形式证明。

自动检查失败时保留原始错误并判断属于实现、环境还是验收标准，不应为了绿灯删除失败测试。形式证明只证明写出的性质；真实需求有误时，一份漂亮证明同样不能交付正确产品。

## 模拟面试问题

1. 基础理解：规则、程序、模型和形式验证各自有什么能力边界？
2. 实际应用：订单查询为什么不能只用状态码和 Schema 验收？
3. 实际应用：如何把模糊的“代码质量好”转成可检查目标？
4. 深入追问：模型评审为什么可能和生成器共享错误？
5. 深入追问：阶段记录怎样帮助失败恢复与成本控制？
