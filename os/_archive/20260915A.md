# 20260915A 操作系统学习笔记

## 一、线程的状态

线程常见的基本状态：

- **就绪态（Ready）**：线程已经具备运行条件，只是在等待 CPU。
- **运行态（Running）**：线程正在 CPU 上执行。
- **阻塞态 / 等待态（Blocked / Waiting）**：线程正在等待某个事件或资源，即使此时给它 CPU 也无法继续执行。

基本状态转换：

```text
就绪态 --获得CPU--> 运行态
运行态 --时间片用完/被抢占--> 就绪态
运行态 --等待资源或事件--> 阻塞态
阻塞态 --资源/事件满足--> 就绪态
```

一个重要结论：

> 阻塞结束后，线程通常先回到就绪态，而不是直接进入运行态。

### 常见“等待”对应的状态

```text
等 CPU   → 就绪态
等锁     → 阻塞态 / 等待态
等磁盘IO → 阻塞态 / 等待态
```

核心判断：

> **只缺 CPU = 就绪态；缺其他资源或事件 = 阻塞/等待态。**

Java 对线程状态划分得更细，例如：

- `BLOCKED`
- `WAITING`
- `TIMED_WAITING`

其中 `synchronized` 竞争锁时通常对应 `BLOCKED`。

## 二、线程控制块 TCB

TCB 全称：

> **Thread Control Block，线程控制块**

它可以理解为操作系统为每个线程保存的一份“线程档案”。

TCB 中通常包含：

- 线程 ID
- 线程状态
- 程序计数器 PC
- CPU 寄存器现场
- 栈相关信息
- 调度信息
- 其他线程管理信息

核心作用：

> **操作系统通过 TCB 管理线程，并在线程切换时保存、恢复线程的执行现场。**

### TCB 与线程上下文切换

假设线程 A 时间片用完，准备切换到 B：

```text
A 正在运行
↓
保存 A 的 PC、寄存器等现场到 TCB_A
↓
从 TCB_B 恢复 B 之前的现场
↓
B 继续运行
```

这就是线程上下文切换的重要基础。

### TCB 与 PCB 的关系

- **PCB**：进程控制块，描述一个进程。
- **TCB**：线程控制块，描述一个线程。

同一进程中的线程共享很多进程级资源，例如：

- 地址空间
- 代码
- 全局数据
- 打开的文件

但每个线程必须有自己的：

- 线程 ID
- 状态
- PC
- CPU 寄存器现场
- 栈

所以每个线程仍需要独立的 TCB。

## 三、线程的实现

线程实现主要分为：

1. 用户级线程
2. 内核级线程
3. 混合型线程

### 1. 用户级线程

用户级线程由用户态线程库管理。

特点：

- 创建、销毁、切换通常不需要进入内核
- 开销较小
- 经典“多对一”模型中，内核并不知道每个具体用户线程

例如：

```text
用户线程 A
用户线程 B
用户线程 C
      ↓
一个内核线程 K1
```

此时内核只能调度 K1。

如果 A 发起阻塞系统调用，在经典多对一模型下，整个内核线程 K1 会阻塞，因此其他用户线程也无法继续运行。

### 2. 内核级线程

内核级线程由操作系统内核直接管理。

例如：

```text
线程 A → 内核线程 K1
线程 B → 内核线程 K2
线程 C → 内核线程 K3
```

特点：

- 内核能分别调度线程
- 一个线程阻塞，不一定影响其他线程
- 可以利用多个 CPU 核心真正并行
- 创建和切换成本通常高于纯用户级线程

### 3. 混合实现

多个用户线程映射到多个内核线程：

```text
用户线程 A B C D E
        ↓
内核线程 K1 K2 K3
```

希望同时获得：

- 用户态线程管理的轻量
- 内核线程的多核并行能力

---

## 四、多对一、一对一、多对多

### 多对一

```text
A ┐
B ├──→ K1
C ┘
```

特点：

- 用户线程切换轻量
- 底层只有一个内核线程
- 无法真正利用多个 CPU 核心并行

### 一对一

```text
A → K1
B → K2
C → K3
```

特点：

- 可以多核并行
- 一个线程阻塞通常不影响其他线程
- 内核线程数量更多，管理成本较高

### 多对多

```text
A B C D E
  ↓ ↓ ↓
K1 K2 K3
```

特点：

- 用户线程数量可以大于内核线程数量
- 可以利用多核
- 实现更复杂

### 为什么“用户线程不能多核”不严谨

真正决定能否利用多核的是：

> **底层是否存在多个可被内核调度的内核线程。**

因此：

```text
多对一 → 不能真正多核并行
一对一 → 可以多核并行
多对多 → 可以多核并行
```

不是“用户线程”这个身份天然不能多核。

# 五、处理机调度概述

处理机调度解决的问题：

> **当多个进程/线程都想使用 CPU 时，决定接下来让谁运行。**

通常分为三级：

1. 高级调度
2. 中级调度
3. 低级调度

---

## 1. 高级调度

也称作业调度。

作用：

> 从外存中的作业中选择一部分进入内存，并创建为进程。

可以记：

```text
外存中的作业
↓ 高级调度
内存中的进程
```

核心是：

> **作业 → 进程**

---

## 2. 中级调度

也称内存调度。

作用：

> 在内存和外存之间调整已经存在的进程。

包括：

```text
内存 → 外存：挂起 / 换出
外存 → 内存：激活 / 换入
```

所以中级调度当然可以实现“外存 → 内存”的激活。

但：

> **激活 ≠ 直接运行。**

例如：

```text
挂起就绪态
↓ 激活
就绪态
↓ 等待低级调度
运行态
```

若原来是挂起阻塞态：

```text
挂起阻塞态
↓ 激活
阻塞态
```

它仍要继续等待原来的事件。

---

## 3. 低级调度

也称进程/线程调度。

作用：

> 从就绪队列中选择一个进程或线程，让它获得 CPU。

即：

```text
Ready → Running
```

这是执行频率最高的一类调度。

---

## 高级调度与中级调度的区别

两者看起来都可能涉及“外存 → 内存”，但对象不同。

### 高级调度

对象：

> 还没有作为活跃进程进入内存的作业。

作用：

> 选择作业进入内存，建立进程。

### 中级调度

对象：

> 已经存在，只是被挂起的进程。

作用：

> 决定它现在是否应该留在内存中。

一句话：

```text
高级：作业 → 进程
中级：已存在进程 内存 ↔ 外存
低级：就绪进程 → CPU
```

---

# 六、常见处理机调度算法

## 1. 先来先服务 FCFS

全称：

> First Come First Served

规则：

> 谁先进入就绪队列，谁先执行。

例如：

```text
P1 → P2 → P3
```

就按：

```text
P1 → P2 → P3
```

运行。

优点：

- 简单
- 容易实现

缺点：

- 短任务可能被前面的长任务拖住
- 容易出现“护航效应”

### 护航效应

一个很长的任务排在前面，导致后面许多短任务长时间等待。

---

## 2. 短作业优先 SJF

全称：

> Shortest Job First

规则：

> 预计运行时间最短的任务优先执行。

优点：

- 在已知作业运行时间的理想条件下，可以取得较小的平均等待时间

缺点：

- 很难准确知道未来还需要运行多久
- 长任务可能发生饥饿

抢占式版本：

> **SRTF：最短剩余时间优先**

若新到达任务的剩余运行时间更短，可以抢占当前任务。

---

## 3. 优先级调度

规则：

> 优先级高的进程先执行。

注意：

- 有的题目规定数字越大优先级越高
- 有的题目规定数字越小优先级越高

必须看题目要求。

分为：

### 非抢占式

高优先级进程来了，也要等当前进程主动退出 CPU。

### 抢占式

更高优先级进程到达后，可以立即抢占当前低优先级进程的 CPU。

### 饥饿问题

低优先级任务可能长时间得不到 CPU。

解决方法之一：

> **老化 Aging**

等待时间越长，逐渐提升它的优先级。

---

## 4. 时间片轮转 RR

全称：

> Round Robin

规则：

> 每个进程轮流获得一个固定时间片。

例如：

```text
P1 → P2 → P3 → P1 → P2 → ...
```

特点：

- 属于抢占式调度
- 非常适合分时系统和交互式系统

### 时间片太大

会逐渐接近 FCFS。

### 时间片太小

上下文切换非常频繁，调度开销增大。

所以时间片需要折中。

---

## 5. 多级队列调度

核心：

> 将不同类型的进程放到不同的固定队列中。

例如：

```text
高优先级队列：系统进程
中优先级队列：交互进程
低优先级队列：批处理进程
```

不同队列可以采用不同调度算法。

特点：

> 进程进入某个队列后，通常就固定在那里。

---

## 6. 多级反馈队列 MLFQ

核心：

> 进程可以在不同优先级队列之间移动。

典型形式：

```text
Q1：高优先级，短时间片
 ↓ 没执行完
Q2：中优先级，更长时间片
 ↓ 没执行完
Q3：低优先级，更长时间片
```

新进程一般先进入最高优先级队列。

如果很快执行完，说明它像短任务。

如果不断用完时间片仍没执行完，说明它像长任务，就逐步降低优先级。

它综合了：

- 短作业优先思想
- 优先级调度
- 时间片轮转

---

## 7. 基于公平原则的调度

目标：

> 长期来看，让各个可运行任务获得合理比例的 CPU 时间。

可以按：

- 完全平均
- 权重比例

来分配 CPU。

---

# 七、实时调度

实时调度的核心目标不是平均等待时间最短，而是：

> **尽量保证任务在截止时间 Deadline 前完成。**

---

## 1. 实现实时调度的基本条件

通常需要：

1. 提供足够的任务信息
2. 系统具有足够的处理能力
3. 支持适当的抢占机制
4. 具有快速的调度与切换能力

任务信息可能包括：

- 到达时间
- 运行时间
- 截止时间
- 优先级
- 资源需求

---

## 2. 实时调度分类

### 非抢占式实时调度

当前任务未主动结束或阻塞前，其他任务不能抢占。

优点：

- 简单
- 切换少

缺点：

- 实时响应能力较弱

### 抢占式实时调度

更紧急的任务到达后，可以抢占当前任务。

实时性更强。

---

## 3. EDF：最早截止时间优先

全称：

> Earliest Deadline First

规则：

> **截止时间最早的任务优先执行。**

例如：

```text
A：Deadline = 20
B：Deadline = 8
C：Deadline = 15
```

执行顺序：

```text
B → C → A
```

EDF 通常属于：

> **动态优先级调度**

因为谁的 Deadline 最近，谁当前优先级最高。

一句话：

> **EDF：谁最早必须交卷，谁先运行。**

---

## 4. LLF：最低松弛度优先

全称：

> Least Laxity First

核心：

> **松弛度越小，任务越紧急。**

公式：

\[
L = 截止时间 - 当前时间 - 剩余运行时间
\]

例如：

```text
截止时间 = 10
当前时间 = 2
剩余运行时间 = 5
```

则：

\[
L = 10 - 2 - 5 = 3
\]

含义：

> 最多还能再等 3 个时间单位。

### 特殊情况

```text
L = 0
```

说明：

> 现在必须马上执行，不能再等。

```text
L < 0
```

说明：

> 即使立刻开始，也已经不可能按时完成。

---

## EDF 与 LLF 的区别

EDF：

> 看谁的截止时间更早。

LLF：

> 看谁的剩余时间余量更少。

可以记：

```text
EDF：谁最早交卷？
LLF：谁最来不及了？
```

---

# 八、优先级倒置

假设有三个线程：

```text
H：高优先级
M：中优先级
L：低优先级
```

L 先拿到一把锁。

随后 H 需要这把锁：

```text
H 等 L 释放锁
```

此时 M 到达，因为：

```text
M 优先级 > L
```

所以 M 抢占 L。

结果：

```text
H 等 L 的锁
L 想运行并释放锁，但被 M 抢占
M 与这把锁无关，却占着 CPU
```

于是最高优先级 H 被间接拖住。

这就是：

> **优先级倒置 Priority Inversion**

---

## 为什么不能让高优先级线程直接抢锁

因为：

> **CPU 使用权可以抢占，但锁保护的是临界区数据的一致性。**

假设低优先级线程 L 正在：

```text
拿锁
↓
修改共享数据
↓
只改了一半
```

如果高优先级线程 H 此时直接抢走锁，就可能访问处于中间状态的数据，破坏：

- 互斥
- 临界区完整性
- 数据一致性

而且 L 的代码仍然认为自己处于持锁临界区，执行状态会混乱。

所以：

> **高优先级线程一般不能直接剥夺其他线程已经持有的互斥锁。**

---

## 优先级继承

经典解决办法：

> **让持锁的低优先级线程暂时继承高优先级等待者的优先级。**

例如：

```text
H 优先级 = 10
M 优先级 = 5
L 优先级 = 1
```

L 持有 H 需要的锁时：

```text
L 临时优先级 = 10
```

于是 M 不能抢占 L。

过程：

```text
H 等锁
↓
提高 L 的优先级
↓
L 快速运行并释放锁
↓
L 恢复原优先级
↓
H 获得锁
```

一句话：

> **不是把锁抢过来，而是让持锁线程赶紧把临界区执行完。**

---

# 九、死锁概述

死锁通常与对不可抢占资源的竞争有关。

经典例子：

```text
线程 A：
持有 锁1
等待 锁2

线程 B：
持有 锁2
等待 锁1
```

于是：

```text
A 等 B
B 等 A
```

双方都无法继续。

死锁可以概括为：

> **多个进程/线程由于竞争资源形成相互等待，如果没有外部干预，它们都无法继续推进。**

---

# 十、死锁、饥饿、死循环的区别

### 死锁

```text
A 等 B
B 等 A
```

多个执行实体之间互相等待。

### 饥饿

某个进程长期得不到资源或 CPU。

例如：

```text
低优先级进程一直被高优先级进程压着
```

### 死循环

程序自身逻辑一直运行：

```java
while (true) {
}
```

区别：

```text
死锁：想继续，但互相等资源
饥饿：一直得不到机会
死循环：程序自己一直执行
```

---

# 十一、死锁产生的四个必要条件

四个条件必须同时成立：

1. 互斥
2. 请求和保持
3. 不可抢占
4. 循环等待

---

## 1. 互斥条件

一个资源同一时刻只能被一个进程使用。

---

## 2. 请求和保持

进程：

> 已经持有一部分资源，同时又继续申请其他资源。

例如：

```text
A 已经持有 R1
↓
不释放 R1
↓
继续申请 R2
```

---

## 3. 不可抢占

已经分配给某个进程的资源：

> 不能被其他进程强行夺走，只能由持有者主动释放。

---

## 4. 循环等待

存在一个资源等待环：

```text
P1 等 P2
P2 等 P3
P3 等 P1
```

形成：

```text
P1 → P2 → P3
↑           ↓
└───────────┘
```

---

# 十二、死锁处理方法总览

主要有四种：

1. 死锁预防
2. 死锁避免
3. 死锁检测
4. 死锁解除

一句话：

```text
预防：不让必要条件同时成立
避免：每次分配前判断是否安全
检测：允许发生，再检查有没有死锁
解除：发现死锁后处理
```

---

# 十三、死锁预防

核心思想：

> **主动破坏死锁四个必要条件中的至少一个。**

通常互斥条件很难破坏，所以重点处理：

- 请求和保持
- 不可抢占
- 循环等待

---

## 1. 破坏“请求和保持”

要求进程开始前：

> 一次性申请全部需要的资源。

如果全部资源不能同时满足：

> 一个都不给。

优点：

- 可以阻止“拿着一部分资源继续等另一部分资源”

缺点：

- 资源利用率低
- 很多资源可能被长期占着但暂时不用

---

## 2. 破坏“不可抢占”

如果进程已经持有一些资源，又申请新的资源失败：

> 让它释放已有资源，以后再重新申请。

不是所有资源都适合这样做。

例如打印机已经打印一半时，一般不适合简单强行抢占。

---

## 3. 破坏“循环等待”

给所有资源统一编号，要求：

> 所有进程都必须按固定顺序申请资源。

例如：

```text
R1 < R2 < R3
```

只能：

```text
R1 → R2 → R3
```

不能一个线程：

```text
R1 → R2
```

另一个线程却：

```text
R2 → R1
```

这样可以从根本上防止形成资源等待环。

---

# 十四、死锁避免

与预防不同：

> 不直接破坏四个必要条件，而是在每次真正分配资源前判断这次分配是否安全。

如果安全：

> 分配。

如果会把系统带入不安全状态：

> 暂时不分配。

---

# 十五、安全状态与安全序列

如果系统存在某个进程执行顺序，使所有进程最终都能顺利结束，那么系统处于：

> **安全状态**

例如存在：

```text
<P1, P3, P2>
```

使：

```text
P1 完成并释放资源
↓
P3 完成并释放资源
↓
P2 完成
```

则这个顺序叫：

> **安全序列**

重要关系：

```text
死锁状态 ⇒ 一定不安全
```

但：

```text
不安全状态 ⇏ 已经死锁
```

不安全状态只是说明：

> 系统已经无法保证后续一定不会死锁。

---

# 十六、银行家算法

银行家算法用于：

> **死锁避免。**

核心思想：

> 真正分配之前，先假装分配一次，再检查系统是否仍处于安全状态。

---

## 常见数据结构

### Available

当前系统还有多少可用资源。

### Max

每个进程最多可能需要多少资源。

### Allocation

当前已经分配给每个进程多少资源。

### Need

每个进程还最多需要多少资源。

公式：

\[
Need = Max - Allocation
\]

这是必须掌握的公式。

---

## 银行家算法基本步骤

某进程提出资源请求后：

### 第一步

判断：

```text
Request ≤ Need
```

不能超过自己声明的最大需求。

### 第二步

判断：

```text
Request ≤ Available
```

系统当前资源必须够。

### 第三步

进行“试分配”。

### 第四步

执行安全性检查。

找：

```text
Need ≤ 当前可用资源
```

的进程。

假设它能执行完，则回收它占有的资源。

不断重复。

如果最后所有进程都能完成：

> 存在安全序列，可以真正分配。

如果无法找到完整安全序列：

> 撤销这次试分配。

# 十七、资源分配图

资源分配图中有：

- 进程节点
- 资源节点

方向含义：

```text
P → R
```

表示：

> P 正在请求资源 R。

```text
R → P
```

表示：

> R 已经分配给 P。

例如：

```text
R1 → P1
P1 → R2
R2 → P2
P2 → R1
```

形成等待环。

---

## 有环是否一定死锁

需要分类。

### 每类资源只有一个实例

若资源分配图存在环：

> 通常可以判断已经死锁。

### 某类资源有多个实例

有环：

> 不一定已经死锁。

所以不能看到“环”就无条件判断死锁。

---

# 十八、死锁检测与解除

这种思路是：

> 不预防，也不避免，允许系统正常分配资源；发生死锁后再检测和处理。

过程：

```text
运行
↓
可能产生死锁
↓
检测
↓
发现死锁
↓
解除
```

---

## 死锁解除方法

### 1. 终止进程

杀掉一个或多个死锁进程，使它们释放资源。

例如：

```text
A 等 B
B 等 A
```

终止 B：

```text
B 释放资源
↓
A 获得资源
↓
死锁解除
```

### 2. 抢占资源

从某些进程中强行回收资源，分给其他进程。

需要考虑：

- 抢谁的资源
- 抢什么资源
- 被抢占进程如何恢复
- 是否需要回滚

# 十九、本次学习重点速记

## 线程部分

```text
等 CPU   → Ready
等锁     → Blocked / Waiting
等磁盘IO → Blocked / Waiting
```

```text
TCB = 线程档案
PCB = 进程档案
```

```text
多对一 → 不能真正多核并行
一对一 → 可以
多对多 → 可以
```

---

## 调度层次

```text
高级：作业 → 进程
中级：已存在进程 内存 ↔ 外存
低级：就绪进程 → CPU
```

---

## 普通调度算法

```text
FCFS：谁先来谁先跑
SJF：谁短谁先跑
优先级：谁重要谁先跑
RR：每人轮一个时间片
MLQ：固定分队列
MLFQ：可以在队列间移动
公平调度：按公平原则分 CPU
```

---

## 实时调度

```text
EDF：谁的 Deadline 最早谁先跑
LLF：谁的松弛度最小谁先跑
```

公式：

\[
L = Deadline - 当前时间 - 剩余运行时间
\]

---

## 优先级倒置

```text
H 等 L 的锁
M 抢占 L
↓
H 被 M 间接拖住
```

经典解决：

> 优先级继承

---

## 死锁四个必要条件

```text
互斥
请求和保持
不可抢占
循环等待
```

---

## 死锁处理

```text
预防：破坏必要条件
避免：银行家算法，保持安全状态
检测：运行后检查
解除：杀进程 / 抢资源
```

银行家算法最重要公式：

\[
Need = Max - Allocation
\]
