# 04 · 死锁

> 一句话概括：多个执行实体**循环等待**对方手里的不可抢占资源，谁也动不了；应对策略按「事前破坏条件 / 事中判断安全 / 事后检测解除」分为四类。
> （Java 代码层面的死锁两线程反序拿锁，见 → `java/14-多线程与锁.md`；本篇是操作系统理论。）

---

## 一、死锁是什么

```text
线程 A：持有锁1，等待锁2
线程 B：持有锁2，等待锁1
→ A 等 B，B 等 A，无外部干预永远卡死
```

> **死锁 = 多个进程/线程因竞争资源相互等待，没有外部干预就无法推进。**

---

## 二、死锁 vs 饥饿 vs 死循环

| | 死锁 | 饥饿 | 死循环 |
|---|---|---|---|
| 本质 | **互相**等资源 | 一直**得不到**机会 | 程序自己一直跑 |
| 状态 | 全都卡住不动 | 想跑但轮不上 | 在跑，只是停不下来 |
| 例子 | A 等 B、B 等 A | 低优先级永远被压制 | `while(true){}` |
| 涉及方 | 至少两方互相等待 | 单方面受害 | 纯程序逻辑 |

---

## 三、死锁的四个必要条件

**四个必须同时成立**，缺一不死锁：

1. **互斥**：资源同一时刻只能被一个进程使用。
2. **请求和保持**：拿着一部分资源，还去申请新的（不撒手再要）。
3. **不可抢占**：已分配的资源不能被强行夺走，只能等持有者主动释放。
4. **循环等待**：存在等待环 P1→P2→P3→P1。

> 这四个条件是**预防死锁的攻击面**——破坏任意一个即可（见下）。

---

## 四、处理策略总览

| 策略 | 时机 | 思路 |
|---|---|---|
| **预防** | 事前 | 破坏四个必要条件之一 |
| **避免** | 每次分配时 | 分配前判断是否仍安全（银行家算法） |
| **检测** | 运行后 | 允许死锁发生，定期查有没有环 |
| **解除** | 发现后 | 杀进程 / 抢资源 |

```text
预防：不让条件凑齐    避免：每笔分配先验安全
检测：出了事再查      解除：查到后处理
```

---

## 五、死锁预防：破坏条件

互斥条件通常破坏不了（资源本性如此），实际针对另外三个：

| 破坏对象 | 做法 | 代价 |
|---|---|---|
| 请求和保持 | 开始前**一次性申请全部**资源，要不全给要不全不给 | 资源利用率低（占着暂时不用的） |
| 不可抢占 | 要不到新资源就**释放已持有的**，以后重来 | 不是所有资源能抢（打印机打到一半） |
| **循环等待** | 资源统一编号，**所有进程按固定顺序申请** | 最常用、代价最小 |

> 「按序申请」正是 Java 里「统一加锁顺序防死锁」的理论根据（`java/14`）。

---

## 六、死锁避免与安全状态

不破坏条件，而是**每次分配前先判断这次分出去系统是否还安全**。

- **安全状态**：存在某个执行顺序 `<P1, P3, P2>`，让所有进程都能依次拿到资源跑完 → 这个顺序叫**安全序列**。
- 核心关系（易错）：

```text
死锁 ⇒ 一定不安全
不安全 ⇏ 已经死锁     ← 不安全只是「无法保证不死锁」，还没真死
```

---

## 七、银行家算法

> **用途：死锁避免。** 思想：分配前先「假装分一次」，检查系统是否仍安全；安全才真给。

### 四个数据结构

| 结构 | 含义 |
|---|---|
| `Available` | 系统当前剩余可用资源 |
| `Max` | 每个进程**最多**需要多少 |
| `Allocation` | 已分配给每个进程多少 |
| `Need` | 每个进程**还**最多需要多少 |

> **必须记住：`Need = Max − Allocation`**

### 处理一次资源请求的步骤

以进程 P 申请 `Request` 为例：

1. `Request ≤ Need`？——不能超过自己声明的最大需求（超了 = 违约，拒绝）。
2. `Request ≤ Available`？——系统当前必须拿得出来（不够 = 暂时等）。
3. **试分配**：`Available −= Request`、`Allocation[P] += Request`、`Need[P] −= Request`。
4. **安全性检查**：反复找一个 `Need ≤ 当前 Available` 的进程 → 假设它跑完并**归还全部资源** → 直到所有进程都能完成 → 找到安全序列，正式分配；中途找不下去了 → **撤销试分配**，让 P 等待。

---

## 八、资源分配图

图中两类节点：进程 P、资源 R。**边的方向是易错点**：

```text
P → R：P 在请求 R（请求边）
R → P：R 已分配给 P（分配边）
```

例：`R1→P1、P1→R2、R2→P2、P2→R1` 形成 P1、P2 的循环等待。

### 有环一定死锁吗？

| 资源情况 | 有环 ⇒ ? |
|---|---|
| 每类资源**只有一个实例** | ⇒ 死锁 |
| 某类资源有**多个实例** | **不一定**死锁（环上的进程可能等的是别人即将释放的实例） |

> 不能见环就判死锁，先看资源实例数。

---

## 九、死锁检测与解除

思路：不预防不避免，正常分配；**运行中检测**（如资源分配图化简），发现死锁再解除。

解除方法：

1. **终止进程**：杀掉一个或多个死锁进程，释放资源（最简单粗暴；代价看被杀的是谁）。
2. **抢占资源**：从某些进程强行回收资源给别人——要解决抢谁的、抢什么、被抢者怎么恢复（回滚）。

---

## 📌 易错点

1. **不安全状态 = 死锁** ✗——不安全只是失去了「保证不死锁」的能力，是预警不是事故。
2. **有环 ⇒ 死锁** ✗——多实例资源下有环不一定死锁。
3. **预防 vs 避免混为一谈**——预防是**全局**破坏条件（改规则）；避免是**每次分配**时判断（银行家算法）。
4. **银行家算法两道关的顺序**——先查 `Request ≤ Need`（守约）再查 `Request ≤ Available`（够分），语义不同、缺一不可。
5. **把饥饿当死锁**——饥饿的一方没有和别人互相等待，只是长期轮不上。

---

## 🧠 速记口诀

```text
死锁四条件：互斥、请求保持、不可抢占、循环等待——破一即防
预防破条件，避免查安全，检测允许发生，解除杀进程
Need = Max − Allocation
银行家四步：查 Need、查 Available、试分配、找安全序列
图上：P→R 请求，R→P 分配；单实例有环必死，多实例有环未必
死锁互相等，饥饿轮不上，死循环停不下
```
