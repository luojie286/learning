# 03 · 应用层服务与排障

> 一句话概括：DNS 把名字变成 IP，ICMP 负责网络诊断，ping/telnet/ssh 各验证不同层次——排障的原则是"先测真正关心的服务（HTTPS），再逐层向下分辨"。

## 一、DNS 域名解析

DNS 把域名解析为记录（A=IPv4、AAAA=IPv6、CNAME=别名），结果按 TTL 缓存。

```text
浏览器/系统缓存 → 递归解析器 → 根 DNS → 顶级域 DNS（如 .com）→ 权威 DNS → 返回并按 TTL 缓存
```

传统 DNS 用 UDP 53（也支持 TCP 53），现代有 DoH/DoT 加密查询。Java 里 `InetAddress.getByName("www.example.com")` 即可拿到地址。

## 二、ICMP 与 ping

**ICMP 是网络层的控制与诊断协议**——封装在 IP 包里传输，但不属于 TCP/UDP，**不使用端口号**。常见消息：Echo Request/Reply（ping 用）、Destination Unreachable、Time Exceeded（TTL 耗尽，tracert 的原理）。

`ping 域名` 的过程：先 DNS 解析出 IP，再发 ICMP Echo Request，收到 Echo Reply 显示结果。输出解读：`时间=25ms` 是 **RTT 往返时延不是单向**；`TTL=57` 是剩余生存时间，不能当"经过的路由器数"。两种错误要分清：

- **"找不到主机"** = 名称解析阶段就失败了（可能是域名拼错，如 `.comm`；或 DNS 故障），还没发 Echo。
- **"请求超时 ×4"** = 解析出了 IP、Echo 也发了，但没收到回显——不能据此判断 HTTP 服务不可用。

## 三、Telnet 与端口测试

Telnet 本意是远程终端协议（TCP 23，明文，已被 SSH 取代），但它的客户端常被借来**测试任意 TCP 端口能否建连**：`telnet 192.168.1.100 8080`。连上只说明 TCP 连接建立成功，不代表上面跑的是 Telnet 或 HTTP 业务正常。PowerShell 等价工具：`Test-NetConnection 192.168.1.100 -Port 8080`。

**三种检查方式各验证一层**：

| 命令 | 验证什么 | 不能证明什么 |
|---|---|---|
| `ping 主机` | ICMP 可达性、RTT | TCP 端口通、HTTP 正常 |
| `telnet/ Test-NetConnection 主机 端口` | TCP 连接能建立 | 业务协议正常 |
| `curl URL` | HTTP 请求与响应 | 所有接口都正常 |

## 四、SSH：远程管理工具

SSH（TCP 22，加密 + 身份验证）用于安全远程登录 Linux 服务器、执行命令、传文件（scp/sftp）、建隧道。登服务器后常做：`ps aux | grep java` 查进程、`ss -lntp` 看监听端口、`tail -f app.log` 跟日志、`docker ps` 看容器。注意 **SSH ≠ HTTP**：前者是开发者管服务器，后者是用户调 Web API。生产环境避免 root 直连，用普通用户 + sudo。

## 五、VPN 代理下为什么"网页能开但 ping 不通"

**系统代理 ≠ 所有 IP 流量被接管**。浏览器的 HTTPS 请求交给代理客户端转发，而 `ping` 的 ICMP 报文通常**绕过 HTTP/SOCKS 代理**直接走本地网络栈——所以网页正常而 ping 100% 丢包完全可能。

| 模式 | 含义 | 对 ping 的影响 |
|---|---|---|
| 规则模式 | 按域名/IP 规则决定直连或代理 | 只配系统代理时 ping 通常不走代理 |
| 全局模式 | 交给客户端的请求统一走代理 | 不等于接管全部系统流量，ICMP 仍可能绕过 |
| TUN 模式 | 虚拟网卡接管底层 IP 流量 | 是否处理 ICMP 取决于软件实现 |

DNS 也可能走两条路：命令行 ping 用系统 DNS 解析，浏览器可能用代理远端 DNS——**两者解析结果可以不同**；同一域名解析出不同 IP 也不一定异常（CDN/负载均衡）。**结论：ping 失败只说明没收到 ICMP 应答，不等于目标服务不可用。**

## 六、排障命令与判断流程

```cmd
nslookup www.example.com           :: 对比默认 DNS 与指定 DNS（nslookup ... 1.1.1.1）
curl.exe -I https://example.com    :: 测 HTTPS（是否走代理取决于环境变量/配置）
ping 1.1.1.1                       :: 单独测 ICMP
tracert www.example.com            :: 看路由路径，* * * 可能只是该跳不应答
Test-NetConnection host -Port 443  :: 只测 TCP 443
```

判断流程：浏览器能打开 → HTTPS 链路正常，ping 不通优先考虑 ICMP 被过滤/未走代理；浏览器也打不开 → 先查域名拼写 → nslookup 对比 DNS → 查代理规则/TUN → curl 测 HTTPS → 再用 ping/tracert 辅助。

## 📌 易错点

- 把 ping 当 Web 服务探活——ICMP 常被防火墙过滤。
- "找不到主机"和"请求超时"混为一谈——前者是 DNS 阶段，后者是 ICMP 阶段。
- "全局模式 = 所有流量都代理"——普通代理不接管 ICMP。
- 同一域名多个 IP 就当 DNS 污染——CDN/轮询是常态，要多源交叉验证。
- telnet 连上 8080 就当 HTTP 正常——只证明了 TCP 层。

## 🧠 速记口诀

```text
DNS 把名变 IP，缓存递归根顶级权威
ICMP 网络层诊断，不占用任何端口
ping 测回显、telnet 测端口、curl 测应用——各管一层
SSH 管机器、HTTP 管业务、代理管浏览——互不等同
先 curl 后 ping，别把 ICMP 当探活
```
