# 05 · 传输技术与 P2P

> 一句话概括：P2P 让数据在端之间直传，但 NAT 挡住了直连——WebRTC 靠"信令交换 + ICE 路径检测"建连，失败走 TURN 中继；大文件传输靠分块、背压、断点续传三板斧。

## 一、P2P 与客户端-服务器模式

```text
传统中转：A ──数据──> 服务器 ──数据──> B     （服务器带宽是瓶颈）
P2P 直连：A <═══════════════> B            （业务数据直传）
```

P2P 仍可能需要中心服务做登录、发现、信令；穿透失败时回退中继。

## 二、NAT：为什么不能直连对方的私有 IP

```text
A：192.168.1.20 ── 路由器/NAT ── Internet ── 路由器/NAT ── B：192.168.5.30
```

`192.168.x.x` 是私有地址，公网不转发；就算知道对方公网地址，NAT 映射、防火墙、网络策略仍可能拦住入站连接——所以**"知道 IP 就能连"不成立**。

## 三、WebRTC 建连的五个角色

| 概念 | 作用 |
|---|---|
| Signaling（信令） | 交换 Offer/Answer/ICE candidate（WebRTC 不限定用什么协议，常用 WebSocket） |
| SDP Offer/Answer | 协商媒体、编解码、传输参数（**不负责穿透**） |
| ICE | 收集并检测候选路径（host/srflx/relay），选出可用连接 |
| STUN | 帮助端点发现自己的 NAT 映射（**不保证穿透成功**） |
| TURN | 直连失败时中继媒体/数据（消耗服务器带宽） |

```text
A ──Offer──> 信令服务器 ──Offer──> B
A <─Answer── 信令服务器 <─Answer─ B
A <──── ICE candidates 交换 ────> B
        ↓ ICE 连通性检查
    直连成功 或 TURN 中继
```

## 四、媒体轨道 vs DataChannel：两条不同的产品路线

- `RTCPeerConnection` 媒体轨道：实时音视频流，关心时延和码率。
- `RTCDataChannel`：消息与二进制数据，基于 SCTP，默认可靠有序。

**"实时视频传输" ≠ "整个视频文件分块传输"**：前者是直播式（连续播放、低延迟），后者是文件分发（完整性、写盘、断点续传）。选哪条是产品架构决策，不能混为一谈，也不能因为 LAN 里传文件简单就当成直播的替代。

## 五、分块传输（Chunking）

1 GiB 文件按 64 KiB 分块 = 16384 块——不用一次把整个文件读进内存（块大小是示例，实现时考虑双方支持的最大消息尺寸）。消息分两类：

```text
元数据：fileId、文件大小、chunkSize、文件哈希
数据块：fileId、chunkIndex（定位与续传）、binary bytes
```

## 六、背压（Backpressure）

发送快于网络实际能力时缓冲会无限增长。解法：盯 `bufferedAmount`，高于高水位暂停投喂，降到低水位恢复（`bufferedAmountLowThreshold` + `bufferedamountlow` 事件）。背压管的是"别过量排队"，不是可靠性机制。

## 七、断点续传与完整性校验

```text
总块数 10000，已确认持久化 0~6347 → 重连后从 6348 继续
```

关键细节：**DataChannel 收到 ≠ 成功写盘**，续传进度以可恢复的持久化状态为准；乱序写入要用位图记录已收块；最终用 SHA-256 核对源文件与目标文件一致（大文件算哈希也耗时）。直播式方案则不需要这些——再次强调两条路线的技术选择不同。

## 📌 易错点

- "STUN 拿到公网 IP 就能 P2P"——ICE 必须做连通性检查，不行还得 TURN。
- "信令服务器负责传媒体"——信令只交换会话信息，媒体走 P2P 或 TURN。
- "DataChannel 默认可靠有序，应用就不用管了"——进度、持久化、失败恢复、完整性仍要管。
- 分块大小拍脑袋——要考虑最大消息尺寸与兼容性。
- 把续传进度记在"收到回调"里——应以写盘完成状态为准。

## 🧠 速记口诀

```text
私网地址公网不认，NAT 挡路 P2P 难
信令交换 SDP，ICE 试路选候选，STUN 帮忙不保证，TURN 兜底做中继
直播走轨道、传文件走 DataChannel——两码事
分块加序号、背压看水位、续传靠位图、完整性 SHA-256
```
