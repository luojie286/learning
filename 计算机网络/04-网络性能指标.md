# 04 · 网络性能指标

> 一句话概括：衡量网络质量看四个指标——RTT 看快慢、丢包看可靠程度、带宽看容量、抖动看稳定性；卡顿通常是它们共同作用的结果。

## 一、四个指标

| 指标 | 核心问题 | 单位 |
|---|---|---|
| RTT（往返时延） | 一次往返多久 | ms |
| 丢包率 | 多少包没到达 | % |
| 带宽 | 单位时间最多传多少 | Mbps/Gbps |
| 抖动 | 到达时间稳不稳 | ms |

**RTT** 是发出到收到响应的往返时间，**不等同于单向延迟**（两个方向时延可能不对称）。可用 ping 粗略观察，但 ICMP 结果不代表应用层真实体验。RTT 高会让交互、远程调用、数据库访问都变慢，且顺序执行的多个请求时延会累加。

**丢包率 = 丢失包数 / 发送包数 × 100%**（发 1000 丢 20 = 2%）。常见原因：拥塞队列溢出、Wi-Fi 干扰、链路故障。TCP 靠确认重传补救（代价是延迟增加）；UDP 不保证，应用自行重传/纠错；WebRTC 实时媒体用 NACK、FEC 或直接丢帧——**太晚到的视频包已无播放价值**。注意：UDP 不可靠 ≠ "UDP 天生造成丢包"，丢包取决于网络环境。

## 二、带宽：标称、可用、吞吐量不是一回事

```text
标称 100 Mbps ÷ 8 = 理论 12.5 MB/s
```

| 概念 | 含义 |
|---|---|
| 标称带宽 | 设备/套餐标注的链路速率 |
| 可用带宽 | 当前环境实际还能提供的传输能力 |
| 实际吞吐量 | 应用真正成功传输的速率 |
| 视频码率 | 编码后音视频每秒所需比特 |

需求 5 Mbps 而可用只有 3 Mbps，持续发送就会排队、延迟升高、丢包、卡顿。WebRTC 的 `availableOutgoingBitrate`（bit/s）只是**对当前候选路径可用发送速率的估计值**——不是网卡上限、不是实际发送速率、不保证能达到；实际速率要靠两次采样 `bytesSent` 差值除以时间差估算。

## 三、抖动与 JitterBuffer

抖动 = 连续包到达时间间隔的变化程度（不是 RTT 波动）。音频包每 20 ms 发一个，到达间隔若变成 `20、80、5、65、10`，播放就会断续。**JitterBuffer**：接收端先缓存一小段再按计划播放，平滑波动——缓冲太小易卡顿，太大则延迟高，**流畅度与低延迟要权衡**。

## 四、四者的因果关系

```text
可用带宽不足 / 发送过快 → 网络拥塞 → 路由器缓冲区排队
→ RTT 增大 → 抖动增大 → 队列溢出丢包 → 卡顿或降质
```

这是一种常见情况而非必然顺序：无线干扰可直接导致丢包，RTT 低也不代表没抖动。回到同步观影的例子：码率 3 Mbps 时 `availableOutgoingBitrate ≈ 8 Mbps` 有余量，`≈ 2 Mbps` 就该降码率；RTT 升高 → 信令和重传变慢；丢包增加 → 画面破损、音频中断；抖动增加 → 缓冲变大 → 播放延迟变高。

## 📌 易错点

- RTT 100 ms 就当单向 50 ms——往返可能不对称。
- 标称带宽当实际下载速度——协议开销、瓶颈链路、拥塞都会打折。
- "平均延迟低就不卡"——抖动大照样卡。
- `availableOutgoingBitrate` 当网卡上限——它只是路径估计。
- UDP 背丢包的锅——UDP 只是不承诺，丢包是网络的事。

## 🧠 速记口诀

```text
RTT 看快慢、丢包看可靠、带宽看容量、抖动看稳定
8 个 bit 是 1 个 Byte，标称除以八是理论
可用带宽是估计，实际速率靠采样
抖动靠缓冲平滑，大了延迟小卡顿——两难权衡
拥塞一条链：排队→时延→抖动→溢出丢包
```
