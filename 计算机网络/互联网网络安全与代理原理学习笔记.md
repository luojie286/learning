# 互联网网络安全与代理原理学习笔记

> 主题：从 Node.js / PHP / Rust 漏洞讨论出发，串联 URL、DNS、TCP/IP、TLS/HTTPS、CA 证书、中间人攻击、VPN、代理、TUN、Clash 与 Java 后端网络链路。
>
> 说明：本文侧重稳定的技术原理。聊天中出现的具体 2026 年漏洞编号、受影响版本、修复版本及事件细节，未在本笔记中重新完成官方核验，**不要直接将其作为生产安全公告**；实际处置应以官方安全公告和项目依赖扫描为准。

## 1. 首先建立全局模型

用户在浏览器输入 `https://www.example.com:443/api/user?id=123`，一个典型的 HTTPS over TCP 请求依次经历：

```text
输入 URL
  ↓
解析 URL（协议、域名、端口、路径、查询参数）
  ↓
DNS：域名 → IP
  ↓
查询路由表、经网关与互联网路由器转发
  ↓
TCP 三次握手（若为 HTTP/1.1 或 HTTP/2 over TCP）
  ↓
TLS 握手：验证网站证书、协商会话密钥
  ↓
传输加密的 HTTP 请求
  ↓
Nginx / Web Server → Tomcat → Spring MVC → Service → DB
  ↓
HTTP 响应经 TLS 加密返回，浏览器解析/渲染
```

例外：HTTP/3 通常基于 QUIC/UDP，不执行 TCP 三次握手；复用已有连接时也无需每次重新握手。

**核心区分：DNS 负责定位、IP 负责寻址转发、TCP 负责可靠字节流、TLS 负责加密与身份认证、HTTP 负责应用层请求响应。**

### 1.1 URL 组成

```text
https://www.example.com:443/api/user?id=123
│        │               │    │         └─ 查询参数
│        │               │    └─ 路径
│        │               └─ 端口
│        └─ 域名
└─ 协议
```

IP 地址标识网络终点；端口让操作系统将连接交给对应的监听套接字和进程。443 是 HTTPS 默认端口，8080 常作为后端应用端口，但任何合法端口都可以按需配置。

## 2. DNS 域名解析

浏览器想访问域名，通常先查浏览器或系统缓存；未命中时询问配置的递归 DNS 解析器。递归解析器可能使用缓存，必要时查询根域名服务器、顶级域 DNS 和域名权威 DNS。

```text
浏览器/系统 → 递归解析器 →（必要时）根 / TLD / 权威 DNS
                                      ↓
                               返回 A/AAAA 等记录
```

- `A` 记录映射到 IPv4，`AAAA` 映射到 IPv6，`CNAME` 表示别名。
- DNS 解析结果可能受到 CDN、地理位置、缓存 TTL 等影响，并非永远只有一个 IP。
- 传统 DNS 可能明文传输；DoH/DoT 可加密 DNS 查询通道，但不能替代 HTTPS 对网站身份的验证。
- **DNS 污染或欺骗**可让客户端连接到错误 IP；正常的 HTTPS 证书验证通常仍会阻止假站冒充。
- `DNS 泄漏`：应用流量走 VPN/代理，但 DNS 查询绕过隧道、直接发送给本地解析器（是否属于问题取决于隐私目标和分流策略）。

## 3. TCP/IP 与路由

### 3.1 常见五层教学模型

| 层次 | 典型协议/技术 | 职责 |
|---|---|---|
| 应用层 | HTTP、DNS | 应用数据交换 |
| 传输层 | TCP、UDP | 端到端传输 |
| 网络层 | IPv4/IPv6 | IP 寻址、路由 |
| 数据链路层 | Ethernet、Wi-Fi | 局部链路上的帧传输 |
| 物理层 | 光纤、无线电 | 比特传输 |

TLS 通常在应用协议与传输之间提供安全保护，不必机械地硬塞进某一教学层。QUIC 集成传输与 TLS 1.3 相关安全机制。

### 3.2 发包路径与 NAT

```text
你的电脑 → Wi-Fi / 家庭网关 → 运营商 → 多级路由器 → 目标服务器
```

操作系统先查询路由表选出接口和下一跳；数据包在各路由器上逐跳转发。家庭 IPv4 网络常通过 NAT 将内网私有地址及端口映射到公网出口地址及端口。

### 3.3 TCP 三次握手

```text
客户端                      服务端
  │ -------- SYN --------> │
  │ <----- SYN+ACK ------- │
  │ -------- ACK --------> │
```

TCP 提供可靠、有序字节流，涉及序列号、确认、重传、流量控制及拥塞控制。**TCP 连通不等于服务器可信，也不意味着数据已加密**。

## 4. TLS/HTTPS：核心安全机制

HTTPS 可以概括为：**HTTP over TLS**（HTTP/3 的具体承载方式不同）。TLS 的三大重要属性：

1. **身份认证**：验证通信对象是不是预期网站。
2. **保密性**：阻止中间网络设备直接读取应用明文。
3. **完整性**：阻止攻击者无声无息地修改受保护数据。

### 4.1 典型 TLS 1.3 握手（简化）

```text
客户端                                          服务端
 ClientHello（算法、密钥交换参数） ------------>
                 <------------- ServerHello（选定参数）
                 <------------- EncryptedExtensions
                 <------------- Certificate + CertificateVerify
                 <------------- Finished
 Finished ------------------------------------->
                 双方传输受保护的应用数据
```

双方通常采用 ECDHE 等密钥交换机制来派生共享会话密钥；TLS 使用对称加密（如 AES-GCM、ChaCha20-Poly1305）保护大量业务数据。**数字证书不是用来直接加密所有 HTTP 数据的，而是主要用于身份认证。** TLS 1.3 中 ServerHello 后的多数握手消息也有加密保护。

### 4.2 PKI 与证书信任链

```text
根 CA（客户端预先信任的信任锚）
  └─ 签发中间 CA
       └─ 签发网站证书（如 www.example.com）
```

客户端验证时不仅检查签名链，还要检查域名是否匹配（SAN）、时间有效性、证书用途和策略、可能的撤销状态等。浏览器还可能实施证书透明度（CT）政策和浏览器自身的封锁列表。

术语：

- **CA**：证书颁发机构。
- **根 CA**：信任锚，对应根证书常由操作系统或浏览器预置信任。
- **中间 CA**：由上级 CA 授权，可在约束范围内签发下级证书。
- **网站证书**：将网站域名和公钥等信息绑定。
- **私钥**：必须保密；泄露后可能导致身份冒充或证书滥签风险。
- **CRL / OCSP**：证书撤销信息的发布/查询方式；实际客户端对撤销失败的处理策略各异。
- **CT**：公开记录证书签发、辅助发现不当签发；不等于自动杜绝一切伪造证书。

### 4.3 CA 私钥泄露为什么危险？

若攻击者获得具有网站证书签发权限的 CA 私钥，在客户端仍接受该 CA、且其他证书策略未阻止的前提下，攻击者可能制作能通过验证的假证书。这打击的是**身份认证**，不是“直接破解 AES”。

必须同时理解两个限制：

- 攻击者通常还需控制 DNS、局域网网关或网络路径，才能让受害者连接到攻击者。
- 伪造证书**不意味着能直接解密此前抓到的所有 HTTPS 流量**；现代 TLS 常用的前向保密机制能保护历史会话。

## 5. 中间人攻击（MITM）如何发生

### 5.1 攻击者怎样接触到流量？

常见路径有：

1. **DNS 欺骗**：将 `bank.example.com` 错误解析到攻击者控制的 IP。
2. **恶意 Wi-Fi / 网关控制**：攻击者处于网络必经路径上。
3. **局域网 ARP 欺骗**：使同一局域网流量经过攻击者设备（具体能否成功取决于网络防护）。
4. **路由劫持**：错误或恶意的 BGP 路由声明可能重定向部分流量，通常需要更高网络控制能力。

仅仅“攻击者知道网址”不等于有能力截获请求。

### 5.2 有伪造证书的 MITM

```text
浏览器                攻击者中转               真实银行
   │ ==== TLS A ========> │                        │
   │  对方伪装成银行       │ ==== TLS B ==========>  │
   │                      │                        │
```

攻击者分别作为两条 TLS 连接的终点，能读取进入自己代理的 HTTP 明文，再转发给真正的服务器。两个 TLS 连接各自可能加密良好，但浏览器被欺骗了**对方的身份**。

### 5.3 “跳转到假站”不一定意味着地址栏变化

| 手法 | 地址栏域名是否必须变化 |
|---|---|
| HTTP 302 跳转到钓鱼域名 | 通常变化 |
| DNS 将原域名解析到恶意 IP | 不需要变化 |
| 网络路径上的中间人代理 | 不需要变化 |

因此不能仅靠地址栏域名判断连接安全；要依赖证书验证、客户端安全更新等机制。

## 6. VPN 与代理：定义和区别

**一句话：代理负责代替应用连接或转发请求；VPN 通过逻辑网络隧道传递网络流量。** 两者可以组合，不能简单理解成“VPN 一定全局、代理一定只管浏览器”。

| 维度 | VPN | HTTP / SOCKS 等代理 |
|---|---|---|
| 常见作用位置 | IP 层隧道 | 应用层或连接层转发 |
| 典型技术 | WireGuard、IPsec、OpenVPN | HTTP CONNECT、SOCKS5、Shadowsocks |
| 是否加密 | 现代安全 VPN 通常加密 | 由代理协议/传输方式决定 |
| 流量覆盖 | 受路由及分流规则控制 | 受应用设置或透明接管方式控制 |
| 目标网站看到的 IP | 通常是 VPN 出口 | 通常是代理出口 |

### 6.1 VPN 的“包中包”原理

普通连接的数据包：

```text
[内层 IP：目标网站 C] [TCP/UDP] [应用数据]
```

经 VPN 封装后（以某些 UDP 隧道为例）：

```text
[外层 IP：VPN 服务器 B] [UDP] [VPN 头] [已加密的内层 IP 包]
```

流程：客户端把内层 IP 包加密封装 → 运营商按外层目的 IP 送到 VPN 服务器 → VPN 服务器解密、解封装并按配置路由/NAT 转发 → 返回流量通过隧道送回。

运营商通常看得到 VPN 节点 IP、通信时间和流量特征，但看不到被加密的隧道载荷；**VPN 服务商不一定能看到 HTTPS 明文**，因为 HTTPS 通常仍是浏览器到目标网站端到端加密。

### 6.2 全隧道与分流隧道

- **全隧道**：默认路由将大部分网络流量送入 VPN。
- **分流（Split Tunnel）**：只把指定目的地或应用流量送入隧道，其余直连。

具体行为由路由、策略与 DNS 设置决定。

## 7. HTTP 代理、SOCKS5 与本地代理端口

### 7.1 `127.0.0.1:7897` 是什么意思？

`127.0.0.1` 是本机回环地址；`7897` 是某个本地代理进程可能监听的端口，并非远程代理服务器的地址。端口能否支持 HTTP 或 SOCKS5，取决于客户端实际配置（如 mixed-port）。

示例（PowerShell，仅当前会话）：

```powershell
$env:HTTP_PROXY  = 'http://127.0.0.1:7897'
$env:HTTPS_PROXY = 'http://127.0.0.1:7897'
$env:ALL_PROXY   = 'http://127.0.0.1:7897'
```

`HTTPS_PROXY` 的值开头为 `http://`，表示**到代理服务器的协议**为 HTTP，不代表最终 HTTPS 网站变成明文。

### 7.2 HTTP CONNECT

浏览器通过 HTTP 代理访问 HTTPS 网站时，通常先请求：

```http
CONNECT github.com:443 HTTP/1.1
Host: github.com:443
```

代理返回隧道建立成功后，浏览器才在隧道内与目标网站执行 TLS 握手。普通 CONNECT 代理默认只是转发加密字节，不会自动获得 HTTPS 明文。

如果本地代理再选择远程加密节点，则链路大致是：

```text
浏览器 → 本地代理 → [加密代理协议] → 远程节点 → 目标网站
```

规则也可能选择 `DIRECT`，无需经过远程节点。

### 7.3 SOCKS5

SOCKS5 是通用连接代理协议，支持 TCP `CONNECT` 及定义了 UDP `ASSOCIATE`；本身**不保证加密**。客户端可传域名交给代理侧解析，也可自己先解析为 IP，这对 DNS 泄漏与分流有影响。

## 8. Clash / Mihomo 的 TUN、分流与 Fake-IP

### 8.1 为什么有些程序不读取系统代理？

HTTP 代理需要应用或其网络库主动使用代理配置。浏览器、Git、Java 客户端、命令行程序的配置机制并不完全相同，因此可能出现“浏览器能访问，Git 不行”。

### 8.2 TUN 模式

TUN 是虚拟三层网络设备。操作系统根据路由把 IP 数据包送入 TUN，Mihomo 等代理内核再读取包、处理连接，并根据规则选择直连或代理出口。

```text
应用普通 Socket
    ↓
操作系统 IP 栈 / 路由表
    ↓
TUN 虚拟接口
    ↓
Mihomo 规则、连接转发
    ├─ DIRECT
    ├─ 代理节点
    └─ REJECT
```

TUN 是**虚拟网络接口机制**，VPN 是**隧道方案**；两者不是一个概念。是否所有程序都受 TUN 接管，取决于路由、权限、IPv6/UDP、排除规则等。

### 8.3 规则分流（示例）

```yaml
rules:
  - DOMAIN-SUFFIX,github.com,PROXY
  - GEOIP,CN,DIRECT
  - MATCH,PROXY
```

这表示先按域名规则匹配，再根据 IP 地理规则判断，最后采用兜底规则。`PROXY` 需为配置中存在的出口或策略组。

### 8.4 Fake-IP

某些模式下，DNS 响应会返回一个内部使用的虚拟 IP（例如 `198.18.0.25`），代理内核保存“虚拟 IP ↔ 域名”的映射。应用连接虚拟 IP 时，代理仍知道原始域名，便于路由和分流。

Fake-IP 并不意味着目标网站真的部署在该地址。

## 9. VPN、代理、HTTPS 分别保护哪一段？

以浏览器访问 HTTPS 网站、且流量经过加密 VPN 为例：

```text
HTTP 明文
   ↓ 由 TLS 加密
HTTPS 密文
   ↓ 由 VPN 加密和封装
VPN 隧道数据
   ↓ 运营商网络
VPN 出口解开 VPN 层
   ↓ 仍为 HTTPS 密文
真正网站解开 TLS 层
```

| 参与方 | 通常可能看到 | 通常无法直接看到 |
|---|---|---|
| ISP | VPN 节点 IP、流量特征 | VPN 隧道内的明文目的信息 |
| VPN 运营方 | 出口目标 IP、连接元数据、可能的 DNS 请求 | 正常 HTTPS 的 HTTP 明文 |
| 目标网站 | VPN 出口 IP、收到的 HTTP 请求、登录账户 | 原始公网出口 IP（无额外泄漏时） |

例外情况：安装了被代理服务商控制的受信任根 CA，并明确经由 TLS 解密代理转发，代理可能查看 HTTPS 明文；终端被恶意软件控制时也不能依赖网络隧道保证内容安全。

## 10. 连接到 Java/Spring Boot 后端

假设部署结构：

```text
浏览器（HTTPS :443）
   ↓
Linux 内核网络协议栈
   ↓
Nginx（监听 443，TLS 终止）
   ↓ 反向代理 http://127.0.0.1:8080
Spring Boot / Tomcat（监听 8080）
   ↓
Filter → DispatcherServlet → HandlerMapping → Controller
   ↓
Service → Mapper/Repository → MySQL / Redis
   ↓
JSON 响应原路返回
```

示例 Controller：

```java
@RestController
@RequestMapping("/api")
public class UserController {
    @GetMapping("/user")
    public UserVO getUser(@RequestParam Long id) {
        return userService.getById(id);
    }
}
```

`DispatcherServlet` 负责分派 Spring MVC 请求；`HandlerMapping` 找到匹配方法，参数解析器绑定 `id` 参数，方法返回值经过 JSON 序列化写入响应。

若 Nginx 到 Spring Boot 使用 HTTP，只表示该**内部一跳**未使用 TLS；跨越不可信网络时要考虑加密。外部 HTTPS 的 TLS 会话可能在 Nginx 处结束。

Node.js 则是 JavaScript **运行时**，Express/NestJS 是应用框架；类似地，JVM/JDK 与 Spring Boot 也不是同一层级。

## 11. 从漏洞事件学到的安全思维

### 11.1 漏洞发生在哪个层级？

| 类型 | 示例 | 影响判断 |
|---|---|---|
| 运行时/标准库 | Node.js 内置压缩/网络模块 | 看运行时版本及是否触发相应代码路径 |
| 语言生态依赖 | Rust crate / npm 包 | 看锁定版本、依赖树和是否真正使用 |
| 框架/容器 | Express、Spring、Tomcat | 看相关组件和配置 |
| 密码学信任基础 | CA 私钥或证书签发流程 | 看客户端信任库、浏览器策略和撤销/封锁状态 |
| 业务代码 | 身份验证、SQL 注入、越权 | 看具体逻辑与数据流 |

**发现 CVE ≠ 每个项目都能被远程攻击 ≠ 已发生大规模数据泄露。** 要检查：影响版本、调用条件、外网暴露面、认证条件、已有缓解措施、官方修复。

### 11.2 GitHub 托管不等于运行 Node.js 服务

- **GitHub Pages**：通常只托管静态资源；即使构建使用 Node.js，也不等于用户访问时服务器在运行 Node.js 后端。
- **GitHub Actions**：构建/测试步骤可能运行 Node.js，重点关注 `actions/setup-node` 和依赖版本。
- **独立主机、PaaS、容器**：若持续提供 Node.js API，则检查生产运行时版本及外部输入处理路径。

### 11.3 危险配置要避免

不要为了修复 HTTPS 错误就在 Java 中使用“信任所有证书”的 `TrustManager` 或关闭主机名验证。不要随意安装陌生根 CA，尤其是在手机/电脑信任存储中。

## 12. 本机实践与排查命令

### Windows / PowerShell

```powershell
# 查询 DNS
nslookup www.cloudflare.com

# 检查 TCP 443 是否可建立连接（不验证 TLS 身份）
Test-NetConnection www.cloudflare.com -Port 443

# 观察 HTTP/TLS 连接信息，输出依 curl 后端而异
curl.exe -v https://www.cloudflare.com

# 查看代理环境变量
Get-ChildItem Env:*PROXY*

# 查看 Git 的 HTTP 代理配置
git config --global --get http.proxy

# 查看 IPv4/IPv6 路由信息
route print

# 查看 DNS 服务器
Get-DnsClientServerAddress

# 查看 Node.js 实际版本与可执行文件路径
node -v
where.exe node
```

### OpenSSL 证书链观察

```bash
openssl s_client -connect www.cloudflare.com:443 \
  -servername www.cloudflare.com -showcerts
```

`-showcerts` 展示服务端发送的证书，不保证包含根证书，也不单独等于完成严格的浏览器式信任验证。

## 13. 高频面试题与一句话答案

1. **DNS 和 HTTPS 的职责区别？** DNS 找地址；HTTPS/TLS 在访问该地址时验证服务端身份并保护通信。
2. **TCP 三次握手保证安全吗？** 不，它保证连接状态建立，不提供 TLS 身份认证和加密。
3. **为什么证书私钥泄露很危险？** 可能使攻击者冒充身份；若泄露的是可签发证书的 CA 私钥，影响范围更大。
4. **有 CA 伪造能力就能破解历史 HTTPS 吗？** 通常不能，现代 TLS 的前向保密机制阻止单靠证书密钥解密历史会话。
5. **DNS 劫持能直接窃取 HTTPS 密码吗？** 正常证书验证能拦截假站；还需证书验证失效或其他攻击条件。
6. **HTTP 代理与 SOCKS5 区别？** 前者面向 HTTP/CONNECT，后者提供更通用的 TCP/UDP 代理能力；二者本身都不必然加密。
7. **TUN 和 VPN 区别？** TUN 是虚拟三层网卡接口；VPN 是通过隧道联通网络的方案。
8. **为什么打开代理后 Git 仍无法访问？** Git 可能未读取相同代理配置、DNS 或分流规则不同、走了其他协议。
9. **Nginx 和 Tomcat 分别做什么？** Nginx 常负责公网接入、TLS 终止、反向代理；Tomcat 作为 Servlet 容器执行 Java Web 应用。
10. **Node.js 是框架吗？** 不是，是 JavaScript 运行时；Express/NestJS 才是其生态里的框架。

## 14. 推荐复习顺序

**第一阶段：看懂一条请求**

URL → DNS → IP/路由 → TCP → TLS → HTTP → Nginx → Spring MVC。

**第二阶段：分清安全边界**

“连接到谁”与“数据有没有加密”是两回事；理解 CA、证书链、ECDHE、对称加密、MITM。

**第三阶段：掌握代理与系统网络**

HTTP CONNECT → SOCKS5 → 本地代理端口 → VPN 包封装 → TUN → 规则分流 → DNS 泄漏/Fake-IP。

**第四阶段：动手验证**

用 `nslookup`、`curl -v`、`Test-NetConnection`、`route print` 和 `openssl s_client` 对照每个概念；通过 Spring Boot + Nginx 的部署理解实际数据路径。

互联网请求

├─ 处理业务
│  ├─ HTTP 请求/响应
│  └─ Nginx → Tomcat → Spring MVC → DB
├─ 改变流量路径
│  ├─ HTTP 代理 / CONNECT
│  ├─ SOCKS5 / 加密代理
│  ├─ VPN / WireGuard
│  └─ TUN / 分流 / Fake-IP
└─ 工程安全
   ├─ 运行时 vs 框架 vs 依赖
   ├─ CVE 影响条件与补丁
   └─ 不关闭 TLS 验证、不信任陌生 CA
