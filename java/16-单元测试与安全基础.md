# 16 · 单元测试与安全基础

> 一句话概括：**JUnit 让「验证」自动化**（准备 → 调用 → 断言）；**安全这块重概念、轻 API**——先分清编码、哈希、加密不是一回事。

---

## 一、JUnit 单元测试

单元测试 = **自动验证代码是否符合预期**，避免每次改代码都手动跑一遍。

核心流程：

```text
准备数据 → 调用被测试方法 → 得到实际结果 → 断言 → 判断是否符合预期
```

### 1.1 `@Test`

```java
@Test
void testAdd() {
    assertEquals(5, 2 + 3);
}
```

`@Test` 告诉 JUnit：这是一个测试方法。

### 1.2 常用断言

```java
assertEquals(expected, actual);   // 相等
assertTrue(condition);
assertFalse(condition);
assertNull(obj);
assertNotNull(obj);
```

### 1.3 Fixture：`@BeforeEach` / `@AfterEach`

Fixture 指**测试前后准备 / 清理环境**：

```java
@BeforeEach
void setUp() {
    calculator = new Calculator();    // 每个测试方法前都执行
}

@AfterEach
void tearDown() {
    // 清理资源
}
```

执行关系：

```text
@BeforeEach → 某个 @Test → @AfterEach     （每个测试方法都会走一遍）
```

### 1.4 异常测试

```java
assertThrows(
        IllegalArgumentException.class,
        () -> divide(10, 0)
);
```

这里「**抛出异常本身才是预期结果**」，所以测试可以通过。

### 1.5 条件测试

```java
@EnabledOnOs(OS.WINDOWS)   // 仅在指定条件下运行
```

了解即可。

### 1.6 参数化测试

同一套测试逻辑跑多组输入：

```java
@ParameterizedTest
@ValueSource(ints = {2, 4, 6, 8})
void testEven(int n) {
    assertTrue(n % 2 == 0);
}
```

### 掌握要求与练习

重点掌握：`@Test`、`@BeforeEach`、`@AfterEach`、`assertEquals()`、`assertTrue()`、`assertFalse()`、`assertThrows()`。参数化测试知道用法即可。

**值得手写**：自己写一个 `Calculator`（`add()` / `sub()` / `divide()`），再为它写测试——覆盖正常结果、异常、`@BeforeEach`。

> JUnit 是所有「值得手写」清单里**性价比最高**的一项：它让后续每一次改动都能被自动验证。

## 二、加密与安全基础

**这一章不需要背 API，但概念必须分清。**

### 2.1 先把三件事分清楚

| | 目的 | 能否还原原文 |
|---|---|---|
| **编码**（Base64） | 换一种表示形式 | ✅ 任何人都能解码 |
| **哈希**（SHA-256） | 生成数据「指纹」 | ❌ 不可逆 |
| **加密**（AES / RSA） | 保护内容不被看到 | ✅ 用密钥可以还原 |

> **编码 ≠ 加密，哈希 ≠ 加密。** 这是最常见的认知错误。

### 2.2 编码：Base64

```text
hello → aGVsbG8=
```

只是**编码**，不是加密——别人可以直接解码恢复原文，**不要用它保护敏感数据**。

### 2.3 哈希：SHA-256

```text
任意长度数据 → 固定长度摘要
```

特点：

- 很难从哈希值反推原文
- 原文轻微变化，结果变化明显
- 用于**完整性校验、数字签名**

```java
MessageDigest md = MessageDigest.getInstance("SHA-256");
```

> `MD5`、`SHA-1` 已不适合安全用途。

### 2.4 HMAC：带密钥的哈希

```text
数据 + 密钥 → HMAC
```

主要用于验证：

- 数据有没有被篡改
- 对方是否持有共享密钥

常见场景：**API 签名、Webhook、支付接口回调验签**。

### 2.5 对称加密：AES

```text
同一把密钥，既负责加密也负责解密
```

| 优点 | 主要问题 |
|---|---|
| 快、适合大量数据 | 如何安全地交换密钥 |

### 2.6 非对称密码学：RSA / ECC

```text
公钥 → 可以公开
私钥 → 必须自己保存
```

可用于加密、签名或密钥协商，具体取决于算法。

### 2.7 数字签名

核心记忆：

```text
私钥签名，公钥验证
```

目的：验证数据是否被篡改、验证签名者是否持有对应私钥。

```text
加密 → 解决「别人能不能看」
签名 → 解决「是不是你发的、有没有被改」
```

### 2.8 密码存储

用户密码**不能明文保存**，也**不推荐直接 `SHA-256(password)`**（太快，易被彩虹表/暴力破解）。

正确做法：用专门的**密码哈希 / KDF** 并结合随机 `salt`：

```text
bcrypt / Argon2 / PBKDF2 / scrypt

password + salt → 密码哈希算法 → hash
```

数据库只保存哈希结果，不保存可还原的密码。

**Salt 的作用**：两个用户密码都是 `123456`，加上不同的随机 salt 后哈希值完全不同——**防止相同密码表现为相同哈希**，并增强对预计算攻击的抵抗。

### 2.9 密钥交换：Diffie-Hellman / ECDH

双方通过公开网络**协商出共享秘密**，而不需要直接发送最终秘密本身。

> 目前理解作用即可，不需要学数学推导。

### 2.10 数字证书

证书用来证明：

```text
「这个公钥属于谁」
```

通常包含：域名/主体信息、公钥、有效期、颁发机构、**CA 的数字签名**。HTTPS / TLS 大量使用证书机制。

### 2.11 Bouncy Castle

Java 常用的**第三方密码学库 / Provider**，不是某一种加密算法。现阶段知道它是什么即可。

### 掌握要求

必须分清：

```text
编码 ≠ 加密      哈希 ≠ 加密
AES → 对称加密   RSA / ECC → 非对称密码体系
数字签名：私钥签名、公钥验证
密码存储：用专门密码哈希算法 + salt
```

**值得手写**：这一章不需要手写密码学算法，只需调用一次 `Base64` 和 `SHA-256` 理解 API 用法。

> ⚠️ **绝对不要自己实现** AES / RSA / SHA / bcrypt / 数字签名算法——实际项目一律使用成熟库。

## 📌 易错点

1. **把 Base64 当加密用**——它能直接解码，等于没加密。
2. **认为 SHA-256 可以「解密」**——哈希不可逆，只能比对，不能还原。
3. **直接用 `SHA-256(password)` 存密码**——没有 salt，且哈希太快，易被彩虹表攻破；应用 bcrypt / Argon2。
4. **搞反签名与验证用的密钥**——记住「**私钥签名，公钥验证**」，反了就是错的。
5. **`assertThrows` 里忘了用 lambda**——被测试的调用必须包在 `() -> ...` 里，否则异常在断言之前就抛出去了。
6. **`@BeforeEach` 与 `@BeforeAll` 混淆**——前者每个测试方法前都跑一次，后者整个类只跑一次（且必须是 `static`）。
7. **测试里只断言「不抛异常」**——没有断言的测试等于没测，必须校验返回值。

## 🧠 速记口诀

```text
测试三步：准备 → 调用 → 断言；先有断言，才算测试
@BeforeEach 每个测试跑一次，@AfterEach 收尾
异常也是预期结果：assertThrows(异常类, () -> 调用)
编码 ≠ 加密，哈希 ≠ 加密
AES 对称，RSA / ECC 非对称；签名：私钥签、公钥验
密码存储：bcrypt / Argon2 + salt，绝不明文、不用裸 SHA-256
密码学算法一律用成熟库，绝不自己实现
```
