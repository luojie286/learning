# 14 · 多线程与锁

> 一句话概括：**进程管资源、线程管执行**；共享数据并发修改产生竞态条件，用锁把临界区变成互斥。

---

## 一、进程与线程

> **线程是进程中的一个执行流，也是 CPU 调度和执行的基本单位。**

| | 进程 | 线程 |
|---|---|---|
| 定位 | **资源容器** | **执行单位** |
| 拥有 | 独立虚拟地址空间、代码段、数据段、堆、打开的文件、网络连接 | 程序计数器 PC、寄存器、栈、运行状态 |
| 关系 | 一个进程至少含一个线程，可以含多个 | 同一进程内的线程**共享**代码段/数据段/堆/全局变量/打开的文件 |

一句话记住：

> **进程负责资源，线程负责执行。**

同一进程中的多个线程可以并发执行，也可以分别跑在不同 CPU 核心上。

### PCB 与 TCB

| | 全称 | 描述 | 保存内容 |
|---|---|---|---|
| `PCB` | Process Control Block | 进程 | 进程 ID、状态、地址空间、资源信息、打开的文件 |
| `TCB` | Thread Control Block | 线程 | 线程 ID、状态、程序计数器、寄存器、栈指针、调度信息 |

```text
PCB → 描述进程
TCB → 描述线程
```

## 二、为什么需要锁：竞态条件

同一进程的线程**共享数据**：

```java
int count = 0;
```

两个线程同时执行 `count++`，而 `count++` 并不是不可分割的操作：

```text
1. 读取 count
2. count + 1
3. 写回 count
```

交叉执行就会出事：

```text
线程A：读取 count = 0
线程B：读取 count = 0
线程A：写回 1
线程B：写回 1
→ 结果是 1，而不是预期的 2
```

这种现象叫 **竞态条件（Race Condition）**——结果取决于线程调度的时序。

## 三、锁、临界区与「拿到锁」

### 锁是什么

> **锁用于控制多个线程对共享资源的并发访问**——某段受保护的代码，同一时刻只允许一个线程执行。

### 什么是「拿到锁」

「拿到锁」**不是拿到了一个实体物品**，而是：

> **线程获得了执行某段受保护代码的资格。**

```text
线程执行到 synchronized(lock)
   ↓
尝试获得 lock 的所有权
   ↓
成功 → 进入临界区
```

所以「获取锁 / 拿到锁 / 持有锁 / 占有锁」说的是同一件事：**当前线程拥有这把锁，因此可以进入对应临界区**。

### 什么是临界区

> **临界区（Critical Section）= 访问共享资源、且可能产生线程安全问题的一段代码。**

例如多个线程都会执行的 `count++`。加锁是为了保护临界区，**不是把整个程序都锁住**。

### 必须竞争同一把锁

```java
Object lock1 = new Object();
Object lock2 = new Object();

// 线程 A                      // 线程 B
synchronized (lock1) { ... }   synchronized (lock2) { ... }
```

这两段代码**没有任何互斥效果**——A 竞争 `lock1`、B 竞争 `lock2`，各拿各的锁，照样能同时执行。

正确的写法是多个线程**执行同一段代码、竞争同一把锁**：

```java
class Counter {
    int count = 0;
    Object lock = new Object();

    void add() {
        synchronized (lock) {
            count++;
        }
    }
}
```

> **互斥是否成立，关键不在于代码写了几份，而在于多个线程竞争的是不是同一把锁。**

---

## 四、synchronized 的三种写法

```java
// ① 同步代码块：锁是括号里的对象
synchronized (lock) { ... }

// ② 同步实例方法：锁是 this
public synchronized void add() { count++; }
// 等价于 synchronized (this) { count++; }

// ③ 同步静态方法：锁是该类的 Class 对象
public static synchronized void add() { }
// 等价于 synchronized (Counter.class) { }
```

## 五、Lock 与 ReentrantLock

```java
Lock lock = new ReentrantLock();

lock.lock();
try {
    count++;
} finally {
    lock.unlock();     // 必须写在 finally
}
```

`unlock()` 放在 `finally` 的原因：**即使临界区抛异常，也要保证锁能释放**，否则其他线程会被永久阻塞。

| | `synchronized` | `Lock` / `ReentrantLock` |
|---|---|---|
| 使用难度 | 简单 | 需手动配对 |
| 释放 | 自动（出块即释放） | 手动 `unlock()`，必须 `finally` |
| 灵活性 | 较低 | 更高（可中断、可超时、可公平） |

## 六、死锁

> 多个线程**互相等待对方释放资源**，导致所有线程都无法继续执行。

经典情形：

```text
线程A：先拿 lock1，再尝试拿 lock2
线程B：先拿 lock2，再尝试拿 lock1

结果：A 持有 lock1 等 lock2，B 持有 lock2 等 lock1 —— 循环等待，双双卡死
```

### 线程必须同时拿两把锁才能运行吗？

**不是。** 线程本身并不要求必须获得两把锁。

只有当某段代码**自己设计成嵌套获取多把锁**时才会需要：

```java
synchronized (lock1) {
    synchronized (lock2) {   // 执行到这里，线程同时持有 lock1 + lock2
        doSomething();
    }
}
```

所以死锁的本质**不是**「线程天生需要两把锁」，而是：

> **某些代码路径让线程在已持有一把锁时，继续去等待另一把锁；当多个线程形成循环等待，就会死锁。**

破坏死锁的常用思路之一是**统一加锁顺序**——所有线程都按 `lock1 → lock2` 的顺序申请。

## 七、InterruptedException

```java
try {
    Thread.sleep(5000);
} catch (InterruptedException e) {
    System.out.println("线程被中断");
}
```

- 主要发生在**线程处于阻塞 / 等待状态**时，被其他线程调用了 `interrupt()`
- 常见会抛它的操作：`Thread.sleep()`、`thread.join()`、`object.wait()`

核心理解：

> **`interrupt()` 不是强制杀死线程**，而是向线程发送一个「中断请求」。

线程收到中断后，应根据自己的逻辑决定是退出、清理资源，还是恢复中断状态（`Thread.currentThread().interrupt()`）继续。**由被中断的线程自己决定怎么响应**，这一点和「强杀」有本质区别。

## 八、整体逻辑链

```text
同一进程中的线程
   ↓ 共享堆、全局变量等资源
多个线程可能同时修改共享数据
   ↓
产生竞态条件
   ↓
划分临界区
   ↓
使用锁保证互斥
```

```text
共享资源 → 并发访问 → 线程安全问题 → 临界区 → 锁 → 互斥执行
```

### 必须记住的五条结论

1. **进程与线程**：进程是资源分配和保护的重要单位，线程是 CPU 调度和执行的基本单位。
2. **锁**：用于控制多个线程对共享资源的并发访问。
3. **拿到锁**：获得进入对应临界区执行代码的资格。
4. **临界区**：访问共享资源且可能产生线程安全问题的代码区域。
5. **互斥的前提**：多个线程必须竞争**同一把锁**。

### 手写练习建议

**必写**——写一个 `Counter`，两个线程各执行 10000 次 `increment()`，分别测「不加 `synchronized`」和「加 `synchronized`」，观察结果差异：

```java
class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}
```

**建议写一次**——`ReentrantLock` + `lock()` + `try/finally/unlock()`；以及经典死锁（两个线程以相反顺序嵌套拿两把锁），直观感受卡死。

**当前看懂即可**（学 JUC 和 JVM 时再深入）：`ReadWriteLock`、`StampedLock`、AQS、`synchronized` 底层实现、锁升级。

## 📌 易错点

1. **用两把不同的锁保护同一份数据**——看起来加了锁，其实完全没有互斥效果。
2. **`synchronized` 实例方法锁的是 `this`，静态方法锁的是 `Class`**——两者不是同一把锁，不要以为加了 `static` 还是同一个锁。
3. **`ReentrantLock` 忘记写 `unlock()` 或没放 `finally`**——一旦抛异常，锁永久不释放。
4. **以为 `count++` 是原子操作**——它是「读-改-写」三步，必须加锁或改用 `AtomicInteger`。
5. **把 `ConcurrentModificationException` 当成「只会在多线程出现」**——单线程也会（见 `11 · 集合框架`）。
6. **以为 `interrupt()` 会强行终止线程**——它只是发出请求，线程可以不理或不立即响应。
7. **以为死锁的前提是「线程必须持两把锁」**——本质是「持有一把时再去等另一把」形成循环等待。

## 🧠 速记口诀

```text
进程管资源，线程管执行；共享堆和全局变量，各自独有 PC / 寄存器 / 栈
count++ 不是原子：读-改-写三步，交叉执行就丢更新
锁 = 进入临界区的资格；互斥的关键是「同一把锁」
实例方法锁 this，静态方法锁 Class
Lock 手动 unlock，必进 finally
死锁 = 持有并等待 + 循环等待；统一加锁顺序可破
interrupt() 是请求，不是强杀
```
