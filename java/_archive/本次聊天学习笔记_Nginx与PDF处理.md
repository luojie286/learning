# 本次聊天学习笔记：Nginx 与 PDF 解密/扁平化

## 1. Nginx 基础

### 1.1 Nginx 是什么
Nginx 可以理解为放在客户端和后端服务之间的一层“中转站”。

典型结构：

```text
浏览器
  ↓
Nginx :80 / :443
  ↓
Spring Boot :8080
  ↓
MySQL / Redis
```

### 1.2 常见用途

#### 反向代理
用户访问的是 Nginx，Nginx 再把请求转发给真正的后端服务。

```text
用户 → Nginx :80 → Spring Boot :8080
```

#### 负载均衡
如果后端有多个实例：

```text
             → Java 服务 1
用户 → Nginx → Java 服务 2
             → Java 服务 3
```

Nginx 可以把请求分配给不同服务器，从而减轻单台服务器压力。

#### 静态资源服务
HTML、CSS、JavaScript、图片等静态文件可以直接由 Nginx 返回，不必经过 Spring Boot。

#### HTTPS 入口
实际部署中，Nginx 也常负责：

- 监听 443 端口
- 配置 SSL/TLS 证书
- 接收 HTTPS 请求
- 将请求转发给内部 HTTP 服务

### 1.3 当前阶段需要掌握的程度
先掌握以下三个关键词即可：

- 反向代理
- 负载均衡
- 静态资源

等真正部署 Spring Boot 项目时，再手写一次最简单的 `server` 和 `proxy_pass` 配置。

## 2. PDF“解密”到底是什么

PDF 的“解密”不一定只是输入密码。

PDF 可能存在多种限制：

1. 打开密码
2. 权限密码
3. 禁止复制、编辑、打印等权限
4. 内嵌文件 / 附件
5. 表单、注释等特殊对象

因此：

> “PDF 能正常打开”不代表“PDF 内部没有加密或特殊结构”。

某些上传系统会进一步检查 PDF 内部对象，即使浏览器能打开，也可能拒绝上传。

---

## 3. 本次 PDF 的处理思路

### 3.1 第一步：去除加密限制
原始 PDF 可以正常读取，因此可以重新生成一个不带加密限制的 PDF。

```text
原 PDF
  ↓
解除 PDF 加密/权限限制
  ↓
普通 PDF
```

但这一步之后，上传系统仍提示：

> PDF 文件包含内嵌文件，不允许上传。

说明问题已经不是“加密”，而是 PDF 内部仍然存在上传系统不允许的对象。

---

## 4. “PDF 包含内嵌文件”是什么意思

PDF 不只是“几张页面”。

它实际上是一种容器格式，内部可能包含：

- 字体
- 图片
- JavaScript
- 表单
- 注释
- 文件附件
- 嵌入对象
- 元数据
- 其他 PDF 对象

某些学校、考试或政务上传系统会采用比较严格的安全检查。

因此，即使一个 PDF：

- 页面显示正常
- 没有密码
- 能打印

仍然可能因为内部存在特殊对象而上传失败。

---

## 5. 最稳妥的处理方式：PDF 扁平化

### 5.1 什么叫“扁平化”
最彻底的方式是：

```text
原 PDF 页面
   ↓
渲染成图像
   ↓
重新生成 PDF
```

也就是不再保留原来的 PDF 内部结构，只保留“页面长什么样”。

### 5.2 扁平化会去掉什么
一般会去掉：

- 内嵌附件
- 表单
- 注释
- JavaScript
- 大部分复杂 PDF 对象
- 原始加密限制

所以它非常适合解决：

> “网页可以看，但是上传系统认为 PDF 不合法”

这类问题。

---

## 6. 解密和扁平化的区别

| 操作 | 主要解决的问题 |
|---|---|
| PDF 解密 | 密码、复制/打印/编辑权限等 |
| 删除附件 | PDF 内嵌文件 |
| 删除表单/注释 | 特殊交互对象 |
| PDF 扁平化 | 最大程度去除复杂 PDF 结构 |

如果只是加密问题：

```text
解密即可
```

如果遇到严格上传系统：

```text
解密
  ↓
仍失败
  ↓
扁平化
```

通常更加可靠。

---

## 7. 扁平化的代价

扁平化并不是没有缺点。

### 文字可能无法选中
因为文字已经变成页面图片。

### 文件可能变大
原本 PDF 中的文字占用空间很小，转换为高分辨率图片后可能明显增大。

### 搜索能力下降
Ctrl + F 可能无法搜索文字。

### 清晰度取决于渲染分辨率
如果渲染 DPI 太低，小字可能变模糊。

因此：

> 普通情况下优先保留原生 PDF；只有遇到兼容性、上传限制时再使用扁平化。

---

## 8. 遇到 PDF 上传失败时的排查顺序

```text
上传失败
  ↓
检查文件大小 / 后缀
  ↓
检查是否加密
  ↓
检查是否存在附件、表单、注释
  ↓
重新保存 PDF
  ↓
仍失败
  ↓
将页面渲染并重新生成 PDF（扁平化）
```

如果扁平化之后仍然无法上传，再检查：

- 文件大小限制
- 页数限制
- PDF 版本
- 文件名是否包含特殊字符
- 上传平台自身 Bug
- 平台是否要求特定来源的 PDF

## 9. 与计算机知识的联系

这次 PDF 问题背后其实涉及一个很重要的计算机思想：

> 文件扩展名只表示文件类型，并不代表内部结构简单。

例如：

```text
.pdf
.docx
.apk
.jar
.zip
```

很多文件格式本质上都是复杂的数据容器。

“打开正常”和“内部结构符合另一个系统的规则”是两回事。

```text
程序 A 能读取
≠
程序 B 一定能读取
```

因为不同程序对格式规范、权限、安全检查和兼容性的要求可能不同。

## 10. 本次聊天核心结论

### Nginx
> Nginx 是部署在后端服务前的一层代理服务器，常负责反向代理、负载均衡、静态资源和 HTTPS。

### PDF
记住三个层次：

```text
能打开 PDF
≠
PDF 没有加密/限制

PDF 没有加密
≠
PDF 内部没有特殊对象

PDF 扁平化
≈
只保留页面最终显示结果
```

如果以后再次遇到：

> PDF 可以正常打开，但某个平台拒绝上传

优先考虑 PDF 内部结构、附件、表单、注释以及兼容性，而不只是“是不是有密码”。
