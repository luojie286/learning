# 20260916B3 —— Java JMM 学习笔记

## 1. JMM 是什么

JMM（Java Memory Model，Java 内存模型）规定了：

> 多个线程之间如何读写共享变量，以及一个线程对共享变量的修改在什么条件下必须被其他线程看到。

JMM 主要关注并发中的三个问题：

- **可见性**
- **原子性**
- **有序性**

需要注意：

> JMM 是一种抽象规范，不等同于真实硬件中的 CPU 缓存或物理内存。

---

## 2. JMM 的主内存与工作内存模型

JMM 可以抽象成：

```text
               主内存
            Main Memory
                 │
        ┌────────┴────────┐
        │                 │
线程 A 工作内存       线程 B 工作内存
Working Memory       Working Memory
        │                 │
      CPU 执行           CPU 执行
```

对于共享变量：

```java
int count = 0;
```

线程在使用共享变量时，可以抽象理解为：

```text
主内存中的 count
       ↓
线程工作内存中的副本
       ↓
线程执行计算
       ↓
再写回共享内存
```

因此可能出现：

```text
线程 A 看到 count = 1
线程 B 仍然看到 count = 0
```

这就是可见性问题。

### 注意

“工作内存”只是 JMM 的抽象概念，不能简单等同于：

- CPU L1/L2/L3 缓存
- 寄存器
- 物理内存

实际 JVM 和 CPU 的实现可能涉及这些机制，但 JMM 本身描述的是语言层面的并发规则。

---

# 3. JMM 的三个核心问题

## 3.1 可见性

可见性指：

> 一个线程修改共享变量后，其他线程能否观察到这个修改。

例如：

```java
boolean flag = false;
```

线程 A：

```java
flag = true;
```

线程 B：

```java
while (!flag) {
}
```

如果没有任何同步措施，JMM 不保证线程 B 能及时观察到线程 A 的修改。

使用：

```java
volatile boolean flag = false;
```

可以建立相应的可见性保证。

---

## 3.2 原子性

原子性表示：

> 一个操作在逻辑上不可被拆分为其他线程可以交错执行的多个步骤。

例如：

```java
count++;
```

它不是一个原子操作，大致可以拆成：

```text
读取 count
↓
count + 1
↓
写回 count
```

假设：

```text
count = 0
```

两个线程同时执行：

```text
线程 A                线程 B

读取 0
                      读取 0

计算 1
                      计算 1

写入 1
                      写入 1
```

最终：

```text
count = 1
```

而不是预期的：

```text
count = 2
```

因此：

```java
volatile int count;
count++;
```

仍然不是线程安全的。

`volatile` 并不能把 `count++` 变成一个原子操作。

可以使用：

```java
synchronized
```

或者：

```java
AtomicInteger
```

例如：

```java
AtomicInteger count = new AtomicInteger();

count.incrementAndGet();
```

---

## 3.3 有序性

Java 源码的书写顺序，不一定完全等于底层实际执行顺序。

例如：

```java
int a = 1;
int b = 2;
```

编译器、JIT 或 CPU 可能在不破坏单线程程序语义的前提下进行重排序。

这涉及：

```text
指令重排序
```

JMM 允许一定程度的重排序，但不能破坏 JMM 规定的同步关系。

---

# 4. as-if-serial

对于单线程程序，编译器和 CPU 可以进行优化和重排序，只要：

> 最终表现得像代码按照程序顺序执行一样。

这就是：

```text
as-if-serial
```

例如：

```java
a = 1;
b = 2;
System.out.println(a + b);
```

即使底层改变部分执行顺序，只要单线程结果仍然正确即可。

但：

> as-if-serial 只保证单线程语义，不足以保证多线程程序正确。

---

# 5. 指令重排序为什么会影响多线程

考虑：

```java
int data = 0;
boolean ready = false;
```

线程 A：

```java
data = 100;
ready = true;
```

线程 B：

```java
if (ready) {
    System.out.println(data);
}
```

直觉上会认为：

```text
只要 ready == true
那么 data 一定已经等于 100
```

但如果没有同步关系，不能仅仅依赖源码书写顺序推导线程间可见性。

这也是为什么多线程中需要：

- volatile
- synchronized
- Lock
- Atomic
- 其他 JUC 同步工具

来建立明确的内存语义。

---

# 6. happens-before

happens-before 是 JMM 中最核心的概念之一。

如果：

```text
A happens-before B
```

表示 JMM 保证：

1. A 的执行结果对 B 可见；
2. A 与 B 之间满足 JMM 规定的顺序关系。

注意：

> happens-before 不等于“现实时间上 A 一定先跑完，B 才开始”。

它是一种内存模型上的顺序与可见性保证。

---

# 7. 常见 happens-before 规则

## 7.1 程序次序规则

同一个线程内部：

```java
a();
b();
```

如果按照程序顺序 `a()` 在 `b()` 前面，那么：

```text
a happens-before b
```

---

## 7.2 volatile 规则

对于同一个 volatile 变量：

```text
对 volatile 变量的写
        ↓
happens-before
        ↓
后续对同一 volatile 变量的读
```

---

## 7.3 锁规则

对于同一把锁：

```text
线程 A 释放锁
      ↓
happens-before
      ↓
线程 B 随后获得同一把锁
```

因此 `synchronized` 不仅提供互斥，也提供可见性保证。

---

## 7.4 线程启动规则

调用：

```java
thread.start();
```

之前的操作 happens-before 新线程开始执行后的相关操作。

---

## 7.5 线程终止规则

假设线程 A 完成任务。

另一个线程调用：

```java
thread.join();
```

并成功返回，那么线程 A 在线程结束前的操作，对 join 之后的代码具有可见性保证。

---

## 7.6 传递性

如果：

```text
A happens-before B
B happens-before C
```

那么：

```text
A happens-before C
```

这条规则非常重要。

---

# 8. volatile 与 happens-before

来看经典例子：

```java
class Demo {
    int data = 0;
    volatile boolean ready = false;

    void write() {
        data = 100;
        ready = true;
    }

    void read() {
        if (ready) {
            System.out.println(data);
        }
    }
}
```

假设线程 A 执行 `write()`：

```java
data = 100;
ready = true;
```

线程 B 执行：

```java
if (ready) {
    System.out.println(data);
}
```

如果 B 读到了 A 写入的：

```java
ready == true
```

那么 B 能够观察到：

```java
data == 100
```

原因不是简单的：

> “源码里 data = 100 写在 ready = true 前面。”

而是因为形成了完整的 happens-before 链。

---

# 9. 最关键的推导：为什么 data = 100 不会跑到 volatile 写之后

线程 A：

```java
data = 100;
ready = true;   // volatile 写
```

线程 B：

```java
if (ready) {    // volatile 读
    System.out.println(data);
}
```

这里需要回答一个关键问题：

> 既然 CPU / 编译器可能重排序，那么 `data = 100` 会不会被重排到 `ready = true` 后面？

答案：

> 在这里不能发生这种会破坏 volatile 内存语义的重排序。

JMM 对 volatile 提供了相应的有序性保证。

可以理解为：

```text
线程 A：

data = 100
    ↓

-------------------------
volatile 写边界
-------------------------

ready = true
```

前面的普通写不能被随意重排到 volatile 写之后，从而破坏 volatile 发布语义。

---

# 10. 用 happens-before 严格推导

线程 A 中：

```java
data = 100;
ready = true;
```

根据程序次序规则：

```text
data = 100
    ↓
happens-before
    ↓
ready = true
```

其中：

```java
ready = true
```

是 volatile 写。

线程 B：

```java
if (ready) {
    System.out.println(data);
}
```

如果 B 的 volatile 读读取到了 A 写入的 `true`：

```text
A：volatile 写 ready = true
          ↓
    happens-before
          ↓
B：volatile 读 ready == true
```

同时在线程 B 内部：

```text
读取 ready
    ↓
happens-before
    ↓
读取 data
```

于是根据 happens-before 的传递性：

```text
A：data = 100
      ↓
A：volatile 写 ready = true
      ↓
B：volatile 读 ready == true
      ↓
B：读取 data
```

最终得到：

```text
A 对 data 的写
happens-before
B 对 data 的读取
```

因此线程 B 能够观察到 `data = 100` 这个写入。

---

# 11. 如果 ready 不是 volatile 呢

如果：

```java
int data = 0;
boolean ready = false;
```

线程 A：

```java
data = 100;
ready = true;
```

线程 B：

```java
if (ready) {
    System.out.println(data);
}
```

此时并没有因为普通变量 `ready` 建立线程间的 happens-before 关系。

因此不能通过：

```text
看到 ready == true
```

推出：

```text
一定看到 data == 100
```

这就是同步机制存在的重要原因。

---

# 12. volatile 可以粗略理解成什么

从学习角度，可以暂时把 volatile 理解成：

```text
可见性
+
一定的有序性约束
```

粗略画成：

```text
线程 A

普通写
普通写
   ↓
volatile 写
```

以及：

```text
线程 B

volatile 读
   ↓
普通读
普通读
```

volatile 建立了跨线程的 happens-before 关系。

但是要注意：

```java
volatile int count;
count++;
```

仍然不是线程安全的，因为 `count++` 是复合操作。

# 13. synchronized 与 JMM

很多人只把：

```java
synchronized
```

理解成“加锁”。

实际上它至少涉及：

```text
互斥
+
可见性
+
有序性
```

例如：

```java
synchronized (lock) {
    count++;
}
```

线程 A 退出同步块：

```text
释放 lock
```

线程 B 随后进入同一个同步块：

```text
获得 lock
```

存在：

```text
unlock
   ↓
happens-before
   ↓
lock
```

因此线程 A 在释放锁前的修改，可以被后续获得同一把锁的线程正确观察。

---

# 14. volatile 与 synchronized 对比

可以先这样记：

```text
volatile
├─ 保证可见性
├─ 提供特定有序性保证
└─ 不保证复合操作原子性

synchronized
├─ 互斥
├─ 可见性
├─ 有序性
└─ 可以保护临界区，使复合操作具有整体原子性效果
```

例如：

```java
volatile int count;
count++;
```

不安全。

而：

```java
synchronized (lock) {
    count++;
}
```

可以安全地保护这段临界区。

# 15. Atomic 与 JMM



# 19. 高频易错点

## 易错点 1

错误理解：

```text
volatile 变量永远直接从物理主内存读取。
```

更准确：

> volatile 提供的是 JMM 规定的可见性和有序性语义，不应机械等价为“每次一定去物理 RAM 读取”。

---

## 易错点 2

错误：

```java
volatile int count;
count++;
```

认为线程安全。

实际上：

```text
count++
=
读取
+
加一
+
写回
```

它仍然是复合操作。

---

## 易错点 3

看到：

```java
data = 100;
flag = true;
```

就认为：

> 因为代码顺序如此，所以其他线程看到 flag=true 时一定能看到 data=100。

错误。

真正成立需要：

```text
同步关系
```

例如：

```java
volatile boolean flag;
```

然后通过 happens-before 推导。

---

## 易错点 4

happens-before 不等于现实时间顺序。

它主要是：

```text
JMM 层面的可见性 + 顺序关系
```

# 20. 面试表达

如果面试官问：

## 什么是 JMM？

可以回答：

> JMM 是 Java 内存模型，它定义了多线程环境下共享变量的访问规则，主要解决可见性、原子性和有序性问题。JMM 通过 happens-before 等规则规定不同线程之间的内存可见性和执行顺序，volatile、synchronized 等并发关键字的内存语义都建立在 JMM 之上。

---

## volatile 有什么作用？

可以回答：

> volatile 主要保证共享变量的可见性，并提供特定的有序性保证。对一个 volatile 变量的写 happens-before 后续对同一个变量的读，因此可以用于线程间状态发布。但 volatile 不能保证类似 count++ 这种复合操作的原子性。

---

## 为什么 volatile flag 可以保证看到前面的 data 写入？

可以回答：

> 因为线程 A 中 data 写 happens-before 后面的 volatile 写；volatile 写又 happens-before 线程 B 对该变量的后续 volatile 读；而 volatile 读又在程序顺序上先于线程 B 对 data 的读取。根据 happens-before 的传递性，线程 A 对 data 的写 happens-before 线程 B 对 data 的读，因此具有可见性保证。

---

# 22. 本次学习核心总结

本次最重要的认知不是：

```text
volatile = 从主内存读取
```

而是：

```text
JMM
↓
happens-before
↓
可见性 + 有序性保证
```

尤其是：

```java
data = 100;
flag = true; // volatile
```

不能仅仅因为源码顺序推出：

```text
看到 flag == true
⇒
一定看到 data == 100
```

真正的逻辑是：

```text
data 写
  ↓ 程序次序规则
volatile 写 flag
  ↓ volatile 规则
volatile 读 flag
  ↓ 程序次序规则
data 读
```

再由：

```text
happens-before 传递性
```

得到：

```text
线程 A 的 data 写
happens-before
线程 B 的 data 读
```

这才是 JMM 对该并发模式提供保证的根本原因。

本文关于 JMM、可见性、原子性、有序性、happens-before、volatile、synchronized 与 Atomic 的核心描述符合 Java 内存模型的基本语义。

特别修正并强调了一个容易产生误解的地方：
