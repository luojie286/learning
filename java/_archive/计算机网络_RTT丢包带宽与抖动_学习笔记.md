# 计算机网络学习笔记：RTT、丢包、带宽与抖动

> 适用范围：计算机网络基础、Java 后端网络排障、WebRTC 实时音视频项目（如 AniRoom）。

## 一、整体认识

衡量网络传输质量时，经常关注四个指标：

| 指标 | 英文 | 核心问题 | 常见单位 |
|---|---|---|---|
| 往返时延 | RTT（Round-Trip Time） | 一次往返要多久？ | ms |
| 丢包率 | Packet Loss Rate | 多少包没成功到达？ | % |
| 带宽 | Bandwidth | 单位时间最多能传多少数据？ | Mbps、Gbps |
| 抖动 | Jitter | 数据到达的时间是否稳定？ | ms |

**一句话记忆：RTT 看快慢，丢包看可靠程度，带宽看容量，抖动看稳定性。**

## 二、RTT：往返时延

RTT 指一个数据包（或探测消息）发出，到收到对应响应之间的时间。

```text
A —— 30 ms ——> B
A <—— 30 ms —— B
RTT ≈ 60 ms
```

- 单位通常为 **毫秒（ms）**。
- RTT 不等同于单向延迟；往返两个方向的时延未必相等。
- RTT 高会使交互、请求响应、远程操作显得迟缓。
- 可使用 `ping` 对网络往返时间进行粗略观察，但 ICMP 的测量结果不一定代表应用协议的真实体验。

### 与 Java 后端的联系

服务之间的网络 RTT 过高，会增加远程调用和数据库访问的耗时。对于顺序执行的多个远程请求，时延还可能累加。

## 三、丢包：数据有没有成功到达

丢包表示发送的数据包未能成功到达接收端，或未在统计窗口内被接收。

**丢包率计算：**

$$\text{丢包率}=\frac{\text{丢失的数据包数量}}{\text{发送的数据包数量}}\times100\%$$

例：发送 1,000 个包，丢失 20 个，丢包率为 **2%**。

常见原因：

- 网络设备或链路拥塞，缓存队列溢出。
- Wi-Fi 信号不稳定、无线干扰。
- 链路错误或网络设备故障。

### TCP 与 UDP 的区别

- **TCP**：通过确认、重传等机制尽量保证有序、可靠地交付字节流；丢包可能增加等待和整体延迟。
- **UDP**：协议本身不保证重传或可靠交付；应用可以自行实现重传或纠错机制。
- **WebRTC 实时媒体**：可能采用 NACK 重传、前向纠错或丢帧等手段，但太晚到达的视频包可能已经没有播放价值。

> 注意：**UDP 不保证可靠性，不等于“UDP 天生造成丢包”。** 丢包主要取决于网络环境等因素。

## 四、带宽：每秒能传多少数据

带宽通常表示网络链路的传输容量；实际可用带宽还会受到共享流量、拥塞和路径瓶颈影响。

```text
链路标称带宽：100 Mbps
100 Mbit/s ÷ 8 = 12.5 MB/s（理论单位换算）
```

这里要区分：

| 概念 | 含义 |
|---|---|
| 标称带宽 | 网络设备或套餐标注的链路速率 |
| 可用带宽 | 当前网络环境下还能提供的传输能力 |
| 实际吞吐量 | 应用实际成功传输的数据速率 |
| 视频码率 | 编码后音视频数据每秒大约需要多少比特 |

例如视频发送需求 **5 Mbps**，而可用带宽只有 **3 Mbps**，若持续发送且无法及时调整，就可能出现排队、延迟升高、丢包和卡顿。

### `availableOutgoingBitrate` 是什么？

在 WebRTC 的 `RTCIceCandidatePairStats` 中，`availableOutgoingBitrate` 表示对**当前候选路径可用发送比特率的估计值**，单位是 **bit/s**。

```js
// 假设统计项包含该字段
const availableOutgoingBitrate = 5_000_000;
// 约 5 Mbps
```

它**不是**网卡最大带宽、实际发送速率，也不能保证应用必然达到该速率。实际发送速率可以通过两次采样 `bytesSent` 的差值除以时间差来估算。

## 五、抖动：传输时间是否稳定

抖动（Jitter）反映连续数据包传输时延或接收时间间隔的**变化程度**。常见的 RTP 抖动统计反映包到达间隔相对于发送间隔的变化，并非单纯计算 RTT 的波动。

例如音频包每隔 20 ms 发出：

```text
较稳定的到达间隔：20、21、19、20、20 ms
不稳定的到达间隔：20、80、5、65、10 ms
```

抖动大的影响：

- 语音可能出现短暂停顿或断续。
- 视频可能出现播放不平滑、卡顿。
- 需要更多缓冲来抵消到达时间的不确定性。

### Jitter Buffer（抖动缓冲区）

接收端先缓存一小段音视频数据，再按计划播放，从而平滑网络到达时间的波动。

**代价：**缓冲过小容易卡顿；缓冲过大则会增加播放延迟。因此实时通信需要在**流畅度**与**低延迟**之间权衡。

## 六、四个指标之间的关系

```text
可用带宽不足 / 发送速率过高
            ↓
          网络拥塞
            ↓
      路由器缓冲区排队
            ↓
      RTT 可能增大
            ↓
      抖动可能增大
            ↓
      队列溢出时可能丢包
            ↓
       音视频卡顿或降质
```

这是**一种常见情况**，不是每次拥塞都必然按此顺序发生。例如无线干扰也能引起丢包，RTT 低也不代表一定没有抖动。

## 七、结合 WebRTC / AniRoom 理解

假设你的同步观影项目需要传输约 **3 Mbps** 的视频流。

- `availableOutgoingBitrate ≈ 8 Mbps`：从当前估计看，有一定可用带宽余量，但仍需观察其他指标。
- `availableOutgoingBitrate ≈ 2 Mbps`：已低于目标视频码率，发送端可能需要降低码率，或者播放体验下降。
- **RTT 升高**：信令交互、反馈和部分重传可能更慢。
- **丢包增加**：可能出现画面破损、音频中断等问题。
- **抖动增加**：接收端可能需要更大的缓冲，导致播放延迟增大。

对 Java 后端与 Agent 应用后端而言，不必现在深入 WebRTC 拥塞控制算法，只需要能解释这些指标，并知道如何判断网络性能问题。

## 八、复习自测

1. RTT 为 100 ms，是否意味着单向传输一定为 50 ms？
2. 发送 2,000 个数据包，丢失 40 个，丢包率是多少？
3. 100 Mbps 理论上对应多少 MB/s？为什么实际文件下载通常更慢？
4. 为什么网络平均延迟不高，视频仍可能卡顿？
5. `availableOutgoingBitrate` 与实际发送码率有什么区别？
6. 为什么实时音视频有时不愿意等待数据包重传？
