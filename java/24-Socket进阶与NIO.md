# 24 · Socket 进阶与 NIO

> 一句话概括：TCP 只是可靠字节流，消息边界要应用自己设计（粘包/拆包）；多客户端靠"每连接一线程 + 线程池"，再高并发就上 NIO（Channel/Buffer/Selector），Netty 是 NIO 的成熟框架。

## 一、TCP 是全双工的

连接建立后两端可同时收发，没有固定"谁只能发"：

```text
客户端 ── "Hello Server" ──> 服务器
客户端 <── "收到：..." ─── 服务器
```

## 二、消息边界：粘包与拆包

**TCP 不保留应用消息边界**：一次 `write()` 不对应一次 `read()`。发 `"hello"` + `"world"` 两次，对方可能一次读到 `"helloworld"`（粘包），也可能分三次读到 `"hel"/"lowo"/"rld"`（拆包）。应用必须自定义 framing：

| 方式 | 做法 | 适用 |
|---|---|---|
| 分隔符协议 | 一条消息以 `\n` 结束，配 `readLine()` | 文本协议，聊天室入门首选 |
| 长度前缀协议 | 先传长度字段，再读指定字节 | 二进制/正式协议 |
| 固定长度协议 | 每条消息长度固定 | 适用面窄 |

聊天室文本行协议示例：`LOGIN alice\n`、`CHAT 你好\n`、`ONLINE\n`。注意：消息本身含换行要转义或改长度前缀；长度前缀要约定字段大小、字节序、最大长度。

## 三、多客户端与聊天室模型

`while (true) accept + 线程池` 之上，聊天室的基本模型：

1. 持续 `accept()` 接收连接；2. 每个客户端一个独立读取任务；3. 维护在线连接集合（**要用并发集合保证线程安全**）；4. 收到消息后广播给其他客户端；5. 断开时清理资源与在线状态。

还要考虑写入失败、慢客户端、消息长度上限、读超时。固定大小线程池的局限：任务阻塞在 `read()` 上时排队，队列可能积压——这就是要上 NIO 的动机。

## 四、BIO 与 NIO

| | BIO（阻塞 IO） | NIO |
|---|---|---|
| 表现 | `accept()/read()` 没有数据就阻塞当前线程 | 非阻塞 + Selector 多路复用 |
| 组件 | `ServerSocket` / `Socket` | `Channel`（传输通道）、`Buffer`（缓冲区）、`Selector`（一个线程关注多个连接的就绪事件） |
| 模型 | 一连接一阻塞线程 | 少量线程管大量连接 |
| 要求 | **能独立写代码** | 了解概念 |

两个"不等于"：BIO ≠ 只能单客户端（配多线程照样多客户端）；NIO ≠ 一定单线程（它提供的是更灵活的模型）。

## 五、Netty

建立在 Java NIO 之上的高性能网络框架，封装了事件循环、编解码、粘包拆包处理等。后续做 IM、RPC、游戏服务端时按需学，现阶段知道"它解决了 NIO 的复杂度"即可。

## 六、动手路线

```text
1 单向通信（发一行打印）→ 2 双向（PING/PONG）→ 3 持续会话（循环读、处理断线与 null）
→ 4 多客户端（线程池）→ 5 最小聊天室（文本协议 + 广播）
→ 6 健壮性（长度上限、超时、并发集合）→ 7 NIO/Netty（进阶）
```

**本阶段重点：Socket + IO + 多线程的实际协作，别急着堆框架。**

## 📌 易错点

- 以为 TCP 一次发送 = 对方一次接收——字节流没有这个消息边界。
- `print()` 不换行对方 `readLine()` 会一直阻塞。
- 聊天室用普通 `ArrayList` 存连接——并发修改会出事。
- 以为线程池能解决一切——长连接阻塞仍排队。
- BIO 配多线程被说成"过时"——模型无贵贱，场景定选型。

## 🧠 速记口诀

```text
全双工双向流，边界要自己抠
粘包拆包三解法：分隔符、长度前缀、定长
一连接一任务，集合要并发
BIO 阻塞一一连，NIO 一个 Selector 管一片
Netty 封装 NIO 的脏活
```
